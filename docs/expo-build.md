## expo build & release (bracemark-expo)

How bracemark-expo gets **built** — the local prebuild/Xcode/gradle workflow, the
app config that feeds it, and the two release-only Android concerns (R8
minification, Play upload signing). For what each dependency _is_ and how it's
wired, see [expo-dependencies.md](./expo-dependencies.md); for the one-time
scaffold commands, [setup.md](./setup.md); for which manifest declares which
version, [architecture.md](./architecture.md) — _dependency versions_.

**Everything here is prebuild-time.** `ios/` and `android/` are CNG output —
regenerated by `npx expo prebuild --clean`, and gitignored — so a native change
lands only through `app.config.ts` or a config plugin. A hand-edit in Xcode
survives until the next `--clean` and then is gone, with a clean working tree
the whole time. See _local build workflow_ below for why they aren't committed,
and how to diff a prebuild on demand when you do want the native delta.

#### local build workflow — the npm scripts

Builds are local (**no EAS** — [setup.md](./setup.md), _expo_, for what that
means for `eas.json` and the renamed `eas-build` target): `expo prebuild`
regenerates the native projects, then **Xcode** builds/runs iOS and
`expo run:android` (or gradle) handles Android. The commands live as **real npm
scripts** in
`apps/bracemark-expo/package.json`:

| script            | command                              | when                                                 |
| ----------------- | ------------------------------------ | ---------------------------------------------------- |
| `prebuild`        | `expo prebuild --clean`              | after any `app.config.ts`/plugin/native-dep change   |
| `start`           | `expo start`                         | Metro, for a Debug run from Xcode                    |
| `android`         | `expo run:android`                   | dev build → device                                   |
| `android:release` | `expo run:android --variant release` | release build → device (R8, no Metro)                |
| `android:reverse` | `adb reverse` ×3 (8081, 8787, 8788)  | once per emulator boot, before anything hits the api |
| `android:open`    | `am start` on the dev-client link    | open the installed dev build, every time             |
| `ios`             | `expo run:ios`                       | quick simulator run without opening Xcode            |
| `ios:open`        | `simctl openurl` on the same link    | ” — the simulator twin                               |

Run them either way — `npm run <script>` from `apps/bracemark-expo`, or the
root alias, one per script, under an `expo:` prefix rather than the `dev:` one
`dev:ext`/`dev:site` use: those start a server in seconds, where `expo:ios` is a
multi-minute native build and install, and one prefix for both would hide that.
The root spelling names the platform even where the app-level script could not be
anything else (`adb reverse` is Android by construction), because at the root
they sit in one list and `expo:reverse` next to `expo:ios` would read as if it
applied to both. Extra flags pass straight through at either level:
`npm start -- --clear`, `npm run expo:prebuild -- --platform ios`.

**The root aliases go through `npm run -w`, NOT `nx` — and that is the one place
in this workspace where bypassing nx is the point.** `"expo:start": "npm run
start -w @stxapps/bracemark-expo --"`, and the same shape for the other six. The
tempting spelling is `nx start @stxapps/bracemark-expo`, and it half-works in the
way that costs the most time to diagnose: Metro boots, the port is right, the app
connects — and **there is no QR code and no key menu**, just
`Waiting on http://localhost:8081`. Nothing errors, so it reads as a broken
install rather than a wrapper artifact.

The gate is one line in the Expo CLI — `isInteractive()` is
`!env.CI && process.stdout.isTTY` ([`@expo/cli`,
`src/utils/interactive.ts`](https://github.com/expo/expo/blob/main/packages/%40expo/cli/src/utils/interactive.ts)) —
and everything interactive hangs off it: the QR code, `i`/`a`/`r`/`j`/`w`, the
`s` toggle. Nx runs a task's executor in a **forked** process whose stdout is a
pipe, so `isTTY` is false inside it however you invoke nx from the outside; the
`nx:run-script` executor then checks `PseudoTerminal.isSupported()` — itself
`process.stdout.isTTY && supportedPtyPlatform()` — sees false, and takes its
`nodeProcess` branch, which `spawn`s the script and pipes stdout. Expo sees a
pipe and prints the CI-shaped output. Attaching a real pty to the outer `nx`
does not help, because the check that matters happens a process later.

**Two workspace settings each independently force that path, and both are
deliberate**, which is why this is worth fixing at the alias rather than at nx:

- **`NX_NATIVE_COMMAND_RUNNER=false`**, committed in the workspace-root `.env`
  to stop the Rust pty from sizing itself independently of your terminal (jest,
  next and wrangler wrap at the wrong column when it does; `FORCE_COLOR=1` sits
  beside it to buy the color back). It makes `runTaskInForkedProcess` choose
  `forkProcessLegacy`, which pipes. **This applies to every nx task in the
  workspace** — nothing run through nx here is interactive.
- **`tui.enabled: false`** in `nx.json`, via
  `disablePseudoTerminal = !tuiEnabled && (!initiatingProject || task.continuous)`.
  `start` is `continuous`, so this is true regardless of the initiating project.

Either alone is sufficient: running `NX_NATIVE_COMMAND_RUNNER=true npx nx start
@stxapps/bracemark-expo` under a real pty still prints `Waiting on …` and no QR,
because the second condition still holds. Only turning the TUI on as well would
restore a pty — at the cost of every other task in the workspace rendering in
panes, and of the terminal-width bug the first setting exists to avoid.

It costs nothing here. These seven targets are `continuous` or fire-and-forget,
none is cached, none has `dependsOn`, and each is already a thin passthrough to a
real npm script — so nx contributes nothing but the lost TTY. **This is the
exception to the workspace's "run tasks through nx" rule, and it is limited to
`expo:*`.** `nx start @stxapps/bracemark-expo` still exists and still works for
anything that doesn't need the terminal UI (a Debug run from Xcode never does);
it is just not what the root alias should call. The same reasoning applies
beyond Metro — under nx, `expo run:ios`/`run:android` lose their build spinners
and leave a Metro with no `r`.

**`android:reverse` is a separate script, NOT chained onto `android`.** The
tempting spelling is `expo run:android && adb reverse …`, and it silently never
runs: `expo run:android` builds, installs, launches, and then **holds the
foreground running Metro** — which is why the target is marked `continuous` — so
`&&` fires only after you Ctrl-C, i.e. after the run that needed the forward. The
inverse order (`adb reverse && expo run:android`) fails differently: `adb reverse`
needs a device already attached, so it aborts the whole build on the very case
where nothing is booted yet and `expo run:android` would have booted one.

The lifecycles differ anyway. A reverse is bound to the **adb device connection**
— it survives app reinstalls and relaunches, and is lost only on device reboot or
`adb kill-server`. Chaining it to the build would tie a per-boot concern to a
per-build command, so re-establishing a forward after rebooting the emulator would
mean sitting through a native rebuild. It is idempotent and instant; run it again
whenever you are unsure.

Keeping it out of `android` also keeps that script byte-for-byte what Expo itself
writes, which the next paragraph is about.

**`android:open`/`ios:open` open the dev build by DEV-CLIENT DEEP LINK, not by
its icon.** Both are one line — `am start -a android.intent.action.VIEW -d …` and
`xcrun simctl openurl booted …` — around the same URL:

```
bracemark://expo-development-client/?url=http%3A%2F%2Flocalhost%3A8081%2F%3FdisableOnboarding%3D1
```

`expo-development-client` is expo-dev-launcher's own host, and the two halves of
that link turn off the two screens it otherwise puts in front of the app. `url`
says which bundle to load, so it skips the launcher's "enter the dev server URL"
home screen — which it shows whenever it has no bundle to remember, i.e. after
anything clears app data (a Maestro `clearState`, so any `npm run e2e:mobile`) or
after its 3-day registry TTL. `disableOnboarding=1` sets the dev **menu**'s
`isOnboardingFinished`, the flag behind the sheet that slides up over the loaded
app. Both flags live in cleared-with-everything-else storage
(`expo.modules.devlauncher.recentyopenedapps` and
`expo.modules.devmenu.sharedpreferences` on Android, `NSUserDefaults` on iOS),
which is why "I dismissed that yesterday" doesn't hold.

The param rides on the **inner** URL deliberately: Android reads it off the
parsed manifest URL and iOS off `expoUrl`, both of which are the inner one, so
one link serves both platforms — and the outer link stays free of `&`, which the
device-side shell in `adb shell` would otherwise treat as a job control operator.
`localhost` rather than `10.0.2.2` for the same reason
[e2e.md](./e2e.md) gives for the api and extractor ports: `android:reverse`
carries 8081 too, so the emulator and the simulator take the identical URL. The
e2e flows launch through the same link — `e2e/mobile/flows/subflows/cold-launch.yaml`.

**`android` and `ios` are named the way they are because PREBUILD WRITES
THEM.** When `expo prebuild` creates a native directory it also "Updates
package.json", adding `android`/`ios` (and `start`/`web`) scripts if absent —
so an alternative spelling like `run-android` doesn't replace them, it just
means every `--clean` re-adds a duplicate pair you have to delete again.
Matching Expo's own names makes that step a no-op. `android:release` and
`android:reverse` are the two additions (Expo has neither) and follow the
workspace's `build:staging` colon convention — which is also why a new script
belongs beside `android` under its own name rather than appended to it: the
colon-suffixed spellings are ours to add, `android` and `ios` are Expo's to
write.

**`prebuild` and `start` OVERRIDE `@nx/expo/plugin`'s inferred targets of the
same name** — a package.json script wins over an inferred target (the
bracemark-api `typecheck` precedent). That's not cosmetic: both inferred targets
are wrong for this workflow.

- **`@nx/expo:start` defaults to `--port 19000`** and exports `RCT_METRO_PORT`
  to match. A Debug build launched from Xcode looks for Metro on **8081**, so
  the inferred target yields "Could not connect to development server". Plain
  `expo start` is 8081.
- **`@nx/expo:prebuild` forks the CLI with `--no-install`**, then runs its own
  `installAsync` — and calls `podInstall` **only when `platform === 'ios'`**.
  The default is `platform: all`, so the common invocation regenerates `ios/`
  and never installs the pods; the next Xcode build fails. Plain
  `expo prebuild` installs deps and pods itself. (Both executors are also
  `x-deprecated` — removed in Nx v24.)

The plugin's `run-android`/`run-ios` targets are left alone — they're already
correct `nx:run-commands` wrappers over the same CLI, so they coexist with the
`android`/`ios` scripts as harmless aliases. Also still inferred and usable:
`export`, `serve`, `install`, `submit`, and the renamed `eas-build`.

Two notes:

- **Don't add a `build` script to this app.** npm would treat `prebuild` as its
  implicit pre-hook and regenerate the native projects on every build. (Nothing
  does today — `nx.json` renames the EAS build target to `eas-build` precisely
  so bracemark-expo has no `build`.)
- **`ios/` and `android/` are gitignored** (anchored paths in the root
  `.gitignore` — the committed native sources under `packages/expo-crypto/` and
  `apps/bracemark-expo/modules/` are unaffected). They're CNG output: `--clean`
  deletes them every time, so **nothing hand-edited in Xcode survives**. Every
  native change belongs in `app.config.ts` or a config plugin. The one thing
  that isn't a file — signing — comes from `APPLE_TEAM_ID` in `.env.local`
  (see the app config section below), and it takes **two** plugins to reach both
  targets: core config-plugins' `withDevelopmentTeam` for the app, and the local
  `with-share-extension-build-settings` for the iOS share extension — see _ios
  share extension build settings_ below. With both in place Xcode's automatic
  signing takes it from there and no manual team pick is needed. If Xcode still
  asks on the **app** target, that's the signal `.env.local` wasn't loaded — fix
  the env, don't fix the pbxproj.

**Why not commit `ios/`+`android/` for audit?** The tempting reason is diffing
what an SDK bump or a config-plugin change does to the native projects — but
tracking them buys that badly and costs real safety. `project.pbxproj` churns
on regenerated object UUIDs, so a `--clean` diff is thousands of unreviewable
lines; and once tracked, a hand-edit in Xcode is a **clean** working tree that
silently no longer matches `app.config.ts`, until the next `--clean` destroys
it. The bare (committed-native) workflow is for native code you author by
hand — and every line of that here already lives in tracked directories
prebuild never touches (`packages/expo-crypto/{ios,android}`,
`apps/bracemark-expo/modules/bracemark-share/{ios,android}`). Nothing under
`apps/bracemark-expo/ios|android` is authored. When you do want the diff, take it
on demand instead of carrying it forever:

    npm run prebuild                              # before state
    cp -R apps/bracemark-expo/ios /tmp/ios-before
    …bump the SDK / edit app.config.ts…
    npm run prebuild
    diff -ru /tmp/ios-before apps/bracemark-expo/ios

For a store `.aab`, gradle directly: `cd apps/bracemark-expo/android && ./gradlew
bundleRelease` (needs a real release keystore — the prebuild template signs
`release` with the debug config, which is fine for `run-android:release` on a
device but not for the Play Store).

#### app config — `app.config.ts`, not `app.json`

The generator scaffolds a static `app.json`; this app uses the **dynamic TS
config** instead (`apps/bracemark-expo/app.config.ts`, a plain
`const config: ExpoConfig = {…}; export default config`, the same shape the old
app used). Expo reads either, and `app.config.ts` wins when both exist — so the
rename is the whole migration; nothing in the workspace reads the file
statically (`@nx/expo`'s executors shell out to the Expo CLI).

**One reason, and it's a correctness one:** `ios.appleTeamId` has to come from
the environment, and JSON has no interpolation — the JSON version carried the
literal string `"process.env.APPLE_TEAM_ID"`, which `withDevelopmentTeam` wrote
verbatim into `DEVELOPMENT_TEAM` for every native target. See
[env-files.md](./env-files.md) — _the one non-`EXPO_PUBLIC_` var_ — for where
`APPLE_TEAM_ID` lives and why it's `.env.local`.

Two gotchas if you touch this:

- **`tsconfig.app.json` excludes it.** The config file must sit at the project
  root, but that tsconfig's `include` glob is `**/*.ts` against
  `rootDir: "src"` — left in, `tsc --build` fails with TS6059. (The other
  root-level config files escape only because they're `.js` and `allowJs` is
  off.) So it isn't covered by `nx typecheck`; its `ExpoConfig` annotation plus
  `npx expo config --type prebuild` is the check. Run the latter after editing.
- **A config change needs `npx expo prebuild`** to reach the native projects,
  like any config-plugin change.

#### versions — one key, three consumers ⚠

`app.config.ts` carries **one** version string, the top-level `version`, and the
per-platform `ios.version` / `android.version` overrides are deliberately absent.
The scaffold sets all three, which is the trap: they are read by different
things and disagreeing costs nothing until late.

| reads                                                        | takes                         |
| ------------------------------------------------------------ | ----------------------------- |
| the app's `Info.plist` / `versionName`                       | `ios.version`, else `version` |
| `expo-share-extension` → the extension's `MARKETING_VERSION` | `version` only, always        |
| `expo-constants` → Settings → **About**                      | `version` only, always        |

Scaffolded, this repo had `version: '0.0.0'` with `1.0.0` on both platform
blocks, so all three disagreed at once and **nothing local said so**: the app
bundle shipped `1.0.0`, the iOS share extension shipped
`CFBundleShortVersionString 0.0.0`, and the About screen read `0.0.0 (1)` to the
user. The extension mismatch is the expensive one — the first thing that reports
it is App Store validation rejecting the upload, because every bundle inside an
app has to carry the containing app's version.

So: **bump `version`, and nothing else.** `ios.buildNumber` and
`android.versionCode` stay per-platform because they are genuinely different
concepts (a string iOS increments per upload, an integer Play orders builds by),
and About prints whichever the running platform has. Belt and braces:
`plugins/with-share-extension-build-settings.js` copies the app target's shipped
version onto the extension regardless, so re-adding `ios.version` can't
resurrect the mismatch — see below.

#### ios share extension build settings ⚠

**The `BracemarkShareExtension` target is born with four values wrong that are
right on the app target**, and nothing downstream reports any of them: prebuild
succeeds, the config is valid, and no lint, type or test reads a pbxproj or a
plist. `expo-share-extension` creates the target from a hardcoded build-settings
map (`plugin/build/xcode/addToXCConfigurationList.js`) and a hardcoded
`Info.plist` (`plugin/build/withShareExtensionInfoPlist.js`), and all four gaps
come from those two files:

| value                                          | app target      | share extension, unfixed          | symptom                                                       |
| ---------------------------------------------- | --------------- | --------------------------------- | ------------------------------------------------------------- |
| `DEVELOPMENT_TEAM`                             | `APPLE_TEAM_ID` | absent                            | empty **Team** in Signing & Capabilities                      |
| `IPHONEOS_DEPLOYMENT_TARGET`                   | `18.0`          | literal `15.1`                    | Pods built for a newer iOS than the target links for          |
| `MARKETING_VERSION`, `CURRENT_PROJECT_VERSION` | `ios.version`   | top-level `version`               | App Store rejects the upload on a version the app won't share |
| `CFBundleDisplayName` (plist)                  | `Bracemark`     | `$(PRODUCT_NAME) Share Extension` | "BracemarkShareExtension Share Extension" in the share sheet  |

The local `plugins/with-share-extension-build-settings.js` supplies all four;
the file carries the full reasoning, so this is the short version.

**They have different causes, and only one is about order.**

- **`DEVELOPMENT_TEAM` — order.** Core config-plugins' `withDevelopmentTeam`
  does walk _every_ native target, but it runs before this one exists. `withMod`
  chains mods under the same key so the **last registered runs first**, and
  `getPrebuildConfig` reads `app.config.ts` (registering every entry in
  `plugins`, `expo-share-extension` included) _before_ it applies
  `withIosExpoPlugins`, which is what registers `withDevelopmentTeam`. So it is
  registered last, runs first, and walks a pbxproj that still has exactly one
  native target.
- **`IPHONEOS_DEPLOYMENT_TARGET` — product type.** `expo-build-properties`
  filters its targets to `TargetType.APPLICATION` (`build/ios.js`,
  `updateDeploymentTargetXcodeProject`), so a `com.apple.product-type.app-extension`
  target is skipped **by design** and would still be skipped if it ran last.
  Meanwhile `ios.deploymentTarget` also lands in `Podfile.properties.json`, so
  every Pod _is_ built at 18.0.
- **The versions — a second config key.** The extension's plist takes
  `CFBundleShortVersionString` from `$(MARKETING_VERSION)`, which
  `expo-share-extension` seeds from the **top-level** `config.version`, while the
  app's plist is written from `ios.version`. Nothing is skipped or mistimed; the
  two targets simply read different keys. → _versions_, above.
- **The display name — a hardcoded string.** `"$(PRODUCT_NAME) Share Extension"`,
  and `PRODUCT_NAME` is the target name, so it resolves to "BracemarkShareExtension
  Share Extension" — the label under the icon in the **iOS share sheet**, which
  the Android half of the feature renders as plain "Bracemark" (its
  `ShareActivity` carries no `android:label`, so it inherits the app's).

The consequence worth remembering: **reordering `plugins` fixes neither.** Nor
does fixing it in Xcode — `ios/` is CNG output, so a hand-picked team or a
retyped deployment target dies at the next `--clean`, with a clean working tree
throughout. Left unnoticed, the signing half fails an archive after the wait.

**The fix is a `finalized` mod, deliberately.** A `withXcodeProject` mod would
work for the team, but only if the plugin were listed _before_
`expo-share-extension` in `plugins` — reverse order, per the chaining above — so
a later innocent reorder of that array would silently undo it. Mod **keys**,
unlike mods within a key, have a fixed precedence (`mod-compiler.js`:
`dangerous: -2`, `xcodeproj: -1`, `finalized: 1`), so `finalized` runs after the
whole xcodeproj chain has run and written the file, wherever the array puts it.
It re-reads the pbxproj from disk because by `finalized` there is no
`modResults` to take.

**Re-registering `withDevelopmentTeam` yourself is the tempting alternative —
don't.** Putting `IOSConfig.DevelopmentTeam.withDevelopmentTeam` first in
`plugins` would make a second copy of it run last, and that is a real one-liner.
It buys a silent dependency on array position in exchange, covers only the
signing half, and still leaves a local plugin entry to explain. Expo offers no
knob to re-time its own registration; `finalized` is the supported way to say
"after everything".

**Everything is copied from the app target, not restated.** The deployment
target from its build settings; the versions and the display name from the
`Info.plist` it actually ships, which is the post-resolution truth — every
earlier mod has had its say by `finalized`. So `app.config.ts` stays the only
place any of these live, and a bump can't leave the extension behind. The
versions are written to **every** target, the app included: on the app target
they change nothing that ships (its plist carries literals), but the scaffold
leaves `MARKETING_VERSION = 1.0` there forever and Xcode's target → General →
Identity reads the build setting rather than the plist — so the app target
displays a version it does not ship until they are aligned. The project-level build
configurations keep the template's `15.1` and that is deliberate: target-level
settings win, and upstream leaves the project level alone for the app target
too.

The plugin then asserts, for every `PBXNativeTarget` × build configuration, that
`DEVELOPMENT_TEAM` is present, that `IPHONEOS_DEPLOYMENT_TARGET` matches the app
target's, and that the target's plist — with its `$(BUILD_SETTING)` references
resolved, which is what actually ships — carries the app's version, build and
display name. A loud prebuild failure in place of a silent empty dropdown.
The assertions pass unchanged if either problem is fixed upstream, since the
writes are idempotent; what they catch is a write that missed a target.

Unset `APPLE_TEAM_ID` stays safe, matching `withDevelopmentTeam`: a falsy id is
skipped and no team is written, so a fresh clone still prebuilds and you pick
both teams by hand. → [env-files.md](./env-files.md), _the one
non-`EXPO_PUBLIC_` var_.

**A fifth thing the target is born with wrong, and it is SOURCE rather than
settings.** `expo-share-extension` also copies its own
`ShareExtensionViewController.swift` into the target on every prebuild
(`plugin/build/xcode/addPbxGroup.js`), and that file sizes React Native's root
view to `UIScreen.main.bounds` while adding it to a view the share presentation
has already pushed 72pt down the screen — a frame is in its **superview's**
coordinates, so the whole sheet renders 72pt below the bottom of the display and
the Save button is cut in half. `plugins/with-share-extension-root-view.js`
rewrites that one branch to `frame = view.bounds`. It is a second `finalized`
mod for exactly the reasons above — `ios/` is CNG output and the `.swift` is
re-copied on every prebuild, so an edit in Xcode dies at the next `--clean` —
and it throws rather than no-ops if upstream rewords the branch, because the
failure it prevents is invisible to prebuild, the Swift compiler, lint, types
and every test. Full derivation, and the before/after measurements, in
[share-sheet.md](./share-sheet.md), _the host view is full-screen_.

#### android release minification — R8

Release Android builds run **R8** (shrink + obfuscate) with resource shrinking,
via the `expo-build-properties` plugin in `app.config.ts`:

    ["expo-build-properties", { android: {
      enableMinifyInReleaseBuilds: true,
      enableShrinkResourcesInReleaseBuilds: true } }]

Both are **off by default** — the prebuild template reads
`findProperty('android.enableMinifyInReleaseBuilds') ?: false`, so without this
block `minifyEnabled` is false and any proguard rule anywhere is inert.
`enableShrinkResourcesInReleaseBuilds` **requires** the minify flag (the plugin
throws otherwise). Debug builds are unaffected; `expo-build-properties` is a
prebuild-time config plugin, so a change here needs `npx expo prebuild`.

**Deliberately no `extraProguardRules`.** The old app
(`brace-client/packages/expo/app.config.ts`) carried ~25 hand-written lines;
none of them should be ported, because every one is either dead or now shipped
by the library itself as `consumerProguardFiles` (R8 merges those from each AAR
automatically):

| old rule                                       | why it's not here                                                              |
| ---------------------------------------------- | ------------------------------------------------------------------------------ |
| `com.horcrux.svg.**`                           | shipped by `react-native-svg/android/proguard-rules.pro` (same line, verbatim) |
| Glide / `AppGlideModule` / `ImageHeaderParser` | was for `react-native-fast-image` (not used); `expo-image` ships a superset    |
| `com.facebook.jni.**`, `animal_sniffer`        | shipped by `react-native/ReactAndroid/proguard-rules.pro`                      |
| `com.facebook.hermes.unicode.**`               | that Java package no longer exists in RN 0.81 — dead rule                      |
| okhttp `PublicSuffixDatabase`, conscrypt       | shipped in okhttp's own AAR consumer rules (4.x+)                              |
| MMKV block                                     | not a dependency (expo-sqlite + expo-secure-store instead)                     |
| bouncycastle, slf4j                            | Blockstack-only — gone with the password-unlocked account model                |

Our own native code is covered the same way: `expo-modules-core`'s consumer
rules keep every `expo.modules.kotlin.modules.Module` subclass, which is what
`BracemarkFileCryptoModule` (the `BracemarkCrypto` pod's Kotlin side) is.

**No nitro keep rule either — and specifically not
`-keep class com.margelo.nitro.** { *; }`.** `react-native-nitro-modules` is
the one dependency here that ships no consumer proguard file, so it looks like
the exception. It isn't, for two checked reasons:

- **`react-native-quick-crypto` has no Java/Kotlin classes for R8 to strip.**
  Nitro resolves a hybrid object one of two ways, and only the Kotlin-backed
  one goes through JNI `findClassStatic` by name (`DefaultConstructableObject`,
  invisible to R8). Every one of quick-crypto's ~30 hybrids takes the **C++**
  path — `QuickCryptoOnLoad.cpp` registers each as
  `std::make_shared<HybridArgon2>()` etc., with zero `JHybrid` references. Its
  whole JVM surface is one `QuickCryptoPackage.java` that calls
  `System.loadLibrary`, reached from the generated `PackageList` (so R8 sees
  it). R8 does not touch the `.so`.
- **Nitro's own runtime Kotlin classes are already annotated.**
  `HybridObject`, `Promise`, `ArrayBuffer`, `AnyMap`, `AnyValue`,
  `NativeRunnable`, `ThreadUtils`, and `NitroModules` all carry
  `@com.facebook.proguard.annotations.DoNotStrip` + `@androidx.annotation.Keep`
  — kept by RN's consumer rules and AGP's default `proguard-android.txt`
  respectively. A blanket `com.margelo.nitro.**` keep would add nothing but
  would suppress obfuscation across the package.

So the keep-set stays empty, and each future addition should name the crash it
fixes. That's affordable because **nitro's failure mode is self-diagnosing**:
if a Kotlin-backed hybrid ever is stripped (a future nitro module, or if
`@stxapps/expo-crypto` grows one), the thrown message is literally
_"Couldn't find class `X`! … If you are using ProGuard, add `@Keep` and
`@DoNotStrip` annotations"_ — and note it prescribes annotating the class, not
a blanket keep.

**Only a real release build exercises this** — not jest, not Metro, not `expo
run:android` (debug). Until bracemark-expo has a release/EAS pipeline,
this is configured but unproven; verify with a release build before the first store
submission.

#### android release signing — the Play upload key

The prebuild template signs the `release` buildType with the **debug** config
(there's a `// Caution!` comment saying so). That's fine for
`npm run android:release` on a device, but the Play Store rejects a
debug-signed artifact — so a real `signingConfigs.release` has to get into
`android/app/build.gradle`. **Not by hand:** `android/` is CNG output, so
`npm run prebuild` (`--clean`) deletes the edit every time. There's no signing
surface in app config and none in `expo-build-properties` either, which makes
this the workspace's first **local config plugin**:
`apps/bracemark-expo/plugins/with-android-signing.js`, listed last in
`app.config.ts`'s `plugins`.

It does exactly one thing at prebuild, and it handles **no credential**:
`withAppBuildGradle` inserts a `release { … }` into `signingConfigs` that
_names_ four Gradle properties — `BRACEMARK_UPLOAD_STORE_FILE`,
`…_STORE_PASSWORD`, `…_KEY_ALIAS`, `…_KEY_PASSWORD` — and rewires
`buildTypes.release`'s `signingConfig` from `signingConfigs.debug` to
`signingConfigs.findByName('release') ?: signingConfigs.debug`. The rewrite is
anchored on the template's own `// Caution!` comment so it can't hit the
identical line in the `debug` buildType, and it **throws** if either anchor is
missing — an SDK bump that moves them fails the prebuild instead of silently
producing a debug-signed bundle.

The injection is **unconditional**, and the missing-credential check moved with
it. The plugin can't see the values any more, so it can't decide anything: it
emits a `project.hasProperty(…)` test over all four names and lets Groovy decide
at _build_ time. That is not a straight port of the old config-time no-op,
because the old one was silent in both directions and one of those directions is
a trap:

- **Nothing missing** → the `release` config is created and used.
- **Something missing, debug build** → the config is never created, `findByName`
  returns null, `buildTypes.release` gets the debug config, and Gradle prints a
  `logger.warn` naming the missing properties. A fresh clone still prebuilds and
  still runs `assembleDebug`.
- **Something missing, release build** → **`GradleException`**, naming the
  missing properties. This is the case the old no-op got wrong. A debug-signed
  AAB builds perfectly, takes minutes, and is rejected by the **Play Store** at
  upload, so the only cheap place to fail is configuration time. "Release build"
  is `gradle.startParameter.taskNames` containing `release`, which covers
  `bundleRelease`, `assembleRelease` and `expo run:android --variant release`.

The consequence for reading the generated file: `signingConfigs.release` is in
`android/app/build.gradle` on every machine now, configured or not, so **its
presence proves nothing** about whether signing works. `./gradlew
:app:signingReport` is the check.

**The signingConfig line has two spellings, and the plugin must accept both.**
Groovy's method-call form (`signingConfig signingConfigs.debug`) and the
assignment form (`signingConfig = signingConfigs.debug`) are both valid, and
both were observed on the same machine within one afternoon — `expo prebuild`
fetches `expo-template-bare-minimum` per run, and the versions differ on this.
Matching only the assignment form is what made the first cut of this plugin die
with _could not find `signingConfigs {`_ on a `--clean`. The regex is therefore
`signingConfig\s*=?\s*signingConfigs\.debug`, and the replacement always emits
the **assignment** form (AGP is moving that way, and it matches the debug line
beside it). If you touch that regex, test it against both spellings — the
generated `android/app/build.gradle` can't be the fixture, since the plugin's
own idempotency guard makes it a no-op.

**Nothing about the upload key is inside this repo — not the keystore, not the
passwords, not the path to either.** All four properties live in
`~/.gradle/gradle.properties` (mode `600`), which Gradle merges into every build
on the machine, and the keystore itself sits wherever that file points, outside
the workspace. The repo holds only the four _names_.

That is a deliberate reversal. The credentials used to live in `.env.local`, on
the `APPLE_TEAM_ID` precedent, and `withGradleProperties` copied them into the
generated `android/gradle.properties` on every prebuild — so a release build put
two plaintext keystore passwords inside the worktree of a **public** repo. Both
files were gitignored, so nothing could commit them; the exposure was to
anything that _reads_ the tree without honouring `.gitignore` — a recursive
grep, a backup, an editor index, an AI agent. Naming a Gradle property cannot
leak one, so the class of accident is gone rather than guarded. `APPLE_TEAM_ID`
stays in `.env.local`: it is an identifier, not a credential, and it has to be
readable by `app.config.ts` at config-evaluation time.

**`BRACEMARK_UPLOAD_STORE_FILE` must be an absolute path.** Gradle's `file()`
resolves a relative one against `android/app/`, and the keystore deliberately
lives outside the directory `--clean` deletes. The plugin used to `path.resolve`
it; it can't any more, because the value is invisible to JS — so a relative path
now fails at build time with a missing-keystore error instead of at prebuild.

**Never commit the keystore**: leaking it or losing it both permanently end the
ability to update the Play listing. Google Play App Signing means this is the
**upload** key, so a loss is recoverable by asking Google to reset it — but only
if the app is already enrolled.

**Don't escape `$` in the passwords any more.** That rule was a dotenv rule:
Expo runs `dotenv-expand` over the env files, so an unescaped `$` started a
variable reference and `Bracemark$1MTo` loaded as `Bracemark`. `gradle.properties`
is a **Java properties** file with no interpolation, so the same password is now
written literally as `Bracemark$1MTo` — and a backslash there is an _escape
character_, so carrying the old `Bracemark\$1MTo` spelling across is itself the
bug. Both failure modes surface identically, as a keystore-password error that
says nothing about where the value came from.

Store build: `cd apps/bracemark-expo/android && ./gradlew bundleRelease`. Verify what
actually signed it — `keytool -printcert -jarfile
app/build/outputs/bundle/release/app-release.aab`, or ask gradle before building
with `./gradlew :app:signingReport` (its `Variant: release` block prints the
store path, alias, and fingerprint). `CN=Android Debug` means the Groovy guard
fell through — one of the four properties is missing from
`~/.gradle/gradle.properties`. The `signingConfigs.release` block is present in
`android/app/build.gradle` either way now, so its presence proves nothing —
`signingReport` is the check, since it resolves the properties and prints the
store path and alias **without** the passwords. Don't reach for
`./gradlew :app:properties` to debug this: it prints every property value in the
clear, passwords included.

Two unrelated things had to be fixed before any of that could run, both worth
knowing about because neither is signing and both fail confusingly:

- **`android.versionCode` must be ≥ 1.** It was `0`, and that is not just a
  Play-upload rule — **AGP rejects it at configuration time** (_"versionCode is
  set to 0, but it should be a positive integer"_), failing every Android build
  of every variant. The version _string_ is a different key (`version`, see
  _versions_ above) and irrelevant to this failure; only the code matters to the
  build.
- **The two hand-written native modules called `useManagedAndroidSdkVersions()`**
  (`apps/bracemark-expo/modules/bracemark-share/android/build.gradle` and
  `packages/expo-crypto/android/build.gradle`), which `expo-modules-core@3.0.30`
  does not define — it ships **`useDefaultAndroidSdkVersions`** (sets
  compileSdk/minSdk/targetSdk from the root `ext`). Gradle failed with _Could not
  find method useManagedAndroidSdkVersions()_ and then the misleading follow-on
  _project ':bracemark-share' does not specify `compileSdk`_. Both now call the real
  helper. The Android side of these modules had never been compiled — iOS was
  unaffected, which is why it went unnoticed. If you hand-write another native
  module, copy the four-call preamble from one of these two rather than from an
  older SDK's template.
