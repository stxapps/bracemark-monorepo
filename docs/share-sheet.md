## share sheet (bracemark-expo)

How "share from Safari/Chrome → pick list, add tags → Save → saved locally,
synced in the background" works on mobile. Living reference like
[architecture.md](./architecture.md); the local-first write path it feeds is
[local-first-sync.md](./local-first-sync.md), the taxonomy pickers it minifies
are [editors.md](./editors.md), and the title/image fill-in it defers is
[link-extraction.md](./link-extraction.md).

### the shape

One RN share screen, written once, hosted by two very different native shells:

- **iOS** — a real share extension target generated by
  [`expo-share-extension`](https://github.com/MaxAst/expo-share-extension)
  (config plugin; SDK 54 = v5+). It boots a **separate RN instance in a
  separate process** with its own JS entry (`index.share.js`, registered as
  `shareExtension`), floating over Safari.
- **Android** — a translucent native `ShareActivity` in the **same app
  process** (local Expo module `modules/bracemark-share`, injected by manifest
  merge — no config plugin needed), hosting the same registered RN root
  (`bracemarkShare`) as a bottom sheet over the caller. The intent payload is
  handed to the root as launch options in `onCreate`, so it can't get lost the
  way expo-share-intent's route-into-the-sleeping-main-activity flow lost it.
  The activity declares its own `android:configChanges` — `MainActivity`'s list
  plus `smallestScreenSize` — because it is not portrait-locked and floats over
  a caller that rotates, splits and unfolds when it likes: undeclared, each of
  those destroys the activity and remounts the root from the intent, and a
  half-filled sheet comes back empty. `fontScale` is not in either list.
  `SHARE-ANDROID-001` holds this with an appearance change under a half-filled
  sheet; rotation is a hand check — [e2e.md](./e2e.md), _across a real share
  boundary_.

**Both shells are labelled "Bracemark"**, and only one of them for free.
Android's `ShareActivity` declares no `android:label`, so it inherits the app's;
iOS shows the extension bundle's `CFBundleDisplayName`, which
`expo-share-extension` hardcodes to `"$(PRODUCT_NAME) Share Extension"` —
"BracemarkShareExtension Share Extension" under the icon, in front of the user,
until a local config plugin overwrites it with the app's own.
→ [expo-build.md](./expo-build.md), _ios share extension build settings_.

The process split is the load-bearing difference, and everything below follows
from it:

|                          | Android (same process)                               | iOS (separate process)                                                                                                      |
| ------------------------ | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| taxonomy for the pickers | read live from sqlite                                | **snapshot** JSON in the App Group container                                                                                |
| saving the link          | the real write edge (mutations → items + pending op) | **outbox** JSON file in the App Group container                                                                             |
| sync after Save          | inline `runIncrementalSync` (process is alive)       | best-effort upload from the extension + main app drains outbox on next launch/foreground                                    |
| page fetch after Save    | a **handoff** marker the main app collects           | the outbox drain returns the link it landed                                                                                 |
| session check            | `getSession()`                                       | the snapshot's `owner` gates the form and is stamped on the draft; the shared-Keychain session mirror arms the upload's api |

**The two shells meet at one `AppRegistry` string.** Each native host mounts
its RN root by a registered name — `bracemarkShare` (Android, `index.js`) and
`shareExtension` (iOS, `index.share.js`, expo-share-extension's entry
convention) — and both names resolve to the same `ShareRoot`
(`src/features/share/share-root.tsx`), which normalizes the host's initial props
(`payloadFromInitialProps`) and renders the shared `ShareScreen`. The native
side never references a component directly; it names a string the JS registers.
On Android the intent payload is read in `ShareActivity`'s delegate
(`getLaunchOptions`) and arrives as that root's initial props; on iOS the
payload (plus `preprocessing.js`'s `{ title, url }`) arrives the same way,
through the extension bundle. So the divergent native wiring converges before a
single pixel is drawn.

### what an app-extension process breaks in React Native itself

The process split above is usually about **data** — no sqlite, no settings, no
keychain without an access group. Two things it breaks are not about data at
all: they are React Native features that quietly compute the wrong number
because the APIs they read do not exist in an extension. Both are invisible to
every automated check we have, and both were live in the shipped sheet. One is
repaired in JS; the other needs native code of our own, because a number RN
cannot compute has to come from somewhere. Neither can be found by reading the
share tree — the share tree looks correct.

**Text renders at zero point.** RN scales every piece of text by
`RCTFontSizeMultiplier()` (`React/Base/RCTUtils.mm`), which is
`mapping[RCTSharedApplication().preferredContentSizeCategory].floatValue` —
and `RCTSharedApplication()` returns **nil in an app extension** by design
(`UIApplication.sharedApplication` is unavailable there). The lookup yields nil,
`.floatValue` on nil is **0.0**, that 0 becomes the surface's
`layoutContext.fontSizeMultiplier`, and
`RCTEffectiveFontSizeMultiplierFromTextAttributes` then takes
`fminf(maxFontSizeMultiplier, 0)` — so our 1.3 cap cannot save it and every font
size in the extension resolves to zero. `TextInput` gets the same value by a
different route (`RCTTextInputComponentView` calls `RCTFontSizeMultiplier()`
itself), so a typed character is invisible too.

The symptom is not a crash and not a fallback to the system face: the text nodes
exist, lay out at zero height, carry the right strings, and paint nothing. The
sheet shows a mark with no wordmark, two rows of icons and chevrons with no
labels, a specimen tile with no title or URL, and a filled Save bar with no word
on it — while `maestro hierarchy` reads back `"List: My List"`, `"Tags: none"`,
`"Save"`, `"Close"`, taps route correctly and the pickers filter. **Only a
screenshot shows it.** (The obvious suspect — the embedded Inter face not
reaching the extension target — is a red herring worth ruling out first and
quickly: `expo-share-extension` reads the `expo-font` plugin's `fonts` array
straight out of `app.config.ts` and copies the file into the extension target's
resources AND its `UIAppFonts`. Check the generated
`ios/BracemarkShareExtension/Info.plist` before spending time there. A missing
family falls back to the system face anyway; it does not render nothing.)

`allowFontScaling={false}` is the only lever, and it is what
`expo-share-extension`'s own `Text`/`TextInput` wrappers set — its README calls
this "a font scaling issue". We set the same flag at **our** two chokepoints
(`components/ui/text.tsx`, `components/ui/input.tsx`) rather than importing its
components, so the sheet keeps Inter, `TextClassContext` and the heading roles.
The multiplier cannot be corrected instead of disabled: `ParagraphShadowNode`
overwrites `textAttributes.fontSizeMultiplier` with the layout context's value,
so a hand-passed one is discarded. Nor can the process be detected from JS —
`Dimensions.fontScale` reports a clean 1.0, because its native side
(`RCTAccessibilityManager`) carries the `<= 0` guard `RCTFontSizeMultiplier`
lacks. So the flag is set **explicitly, from `index.share.js`**, which is the
one file that IS the extension process; `lib/font-scale.ts` holds it and the
derivation, and `lib/font-scale.spec.tsx` pins the entry→chokepoint wiring
(the only part of this jest can see). The cost is stated in
[accessibility.md](./accessibility.md), _font scaling_: Dynamic Type does not
reach the iOS share sheet.

**Every keyboard frame RN reports is zero.** `RCTKeyboardObserver.mm` reads the
notification's `UIKeyboardFrameEndUserInfoKey` correctly, then converts it into
window coordinates: `RCTKeyWindow()`, then
`[window convertRect:endFrame fromCoordinateSpace:window.screen.coordinateSpace]`.
`RCTKeyWindow()` returns **nil in an app extension by contract** — its first line
is `if (RCTRunningInAppExtension()) return nil;` — and a message to nil yields
`CGRectZero`. So `Keyboard.metrics()`, every `keyboardWillShow` payload and
therefore `KeyboardAvoidingView` all report `screenY: 0, height: 0`: a plausible
number, not an error.

What that does to KAV is worse than under-lifting. Its lift is
`frame.y + frame.height - (screenY - keyboardVerticalOffset)`, and against
`screenY: 0` that is the panel's WHOLE height plus the offset — padding that
exceeds the surface it pads. The content box collapses to nothing, the panel
shrinks to its own paddings, and `justify-end` parks the remains above the
sheet. No `keyboardVerticalOffset` rescues this; raising it makes the lift
bigger, and it feeds back into KAV's own `onLayout`.

The notification itself is fine — UIKit posts `UIKeyboardFrameEndUserInfoKey` in
SCREEN coordinates, and reading it needs no window. So the number comes from our
own module: `BracemarkShareKeyboard`
(`modules/bracemark-share/ios/BracemarkShareKeyboardModule.swift`) observes
`keyboardWillChangeFrame` and `keyboardWillHide` and emits the keyboard's top
edge in screen points plus the system's animation duration.
`features/share/share-keyboard.ts` turns that into `useShareKeyboard()` —
`max(panelBottomOnScreen - keyboardTop, 0)`, played onto the system's own curve
with `LayoutAnimation` — and `share-kit.tsx` applies it as bottom padding on the
frame. A hide is reported as "top edge = bottom of the screen", so the lift
falls to zero without a special case.

The panel uses the same number a second time: it subtracts it from the bottom
safe-area inset, because a keyboard's frame reaches the bottom of the screen and
so already covers the home indicator the inset is there to clear
([safe-area.md](./safe-area.md)).

**Android reaches the same number from RN's own events, and no longer through
RN's `KeyboardAvoidingView`.** Its `ShareActivity` rides the app's own process,
where RN's keyboard frames are real, and that branch was a plain KAV with
`behavior="padding"` for exactly that reason. It lifted correctly and then did
not come back down. `ReactRootView` sends `keyboardDidHide` with `screenY` set
to `getWindowVisibleDisplayFrame().height()` — a length that leaves out the
status and navigation bars — and KAV on Android runs a hide through the same
`frame.y + frame.height - screenY` as a show. Under edge-to-edge the frame spans
the whole window, so the "hidden" keyboard still overlapped it by both bars:
`screenY: 840` against a 914dp window on the Pixel 8 AVD, and the panel parked
74dp above the bottom of the screen with the keyboard gone, until the sheet was
reopened. Nothing catches it — the first show is right, and so is every frame
until the first dismissal. (It is the "phantom inset once the keyboard closes"
that [soft-keyboard.md](./soft-keyboard.md) records for the portaled dialog.)

So the hook listens to the same two events and trusts only what is true in
them: `keyboardDidShow`'s `height`, and the FACT of a `keyboardDidHide`. That
height is the IME inset minus the system bars' inset — measured from the top of
the navigation bar, while the frame runs underneath it — so the hook adds the
bottom safe-area inset back, which makes it the IME inset itself: the window's
own account of how much of its bottom the keyboard covers. Driven on the AVD
under both gesture and 3-button navigation: the panel's bottom edge lands on the
keyboard's top edge (577.9dp) either way and returns flush to the screen bottom
on back and on a tap in the panel. Both hosts therefore end in one `View` with
bottom padding on the same `justify-end` column, which is what keeps one tree
serving two hosts. Not react-native-keyboard-controller, because this file also
renders inside the extension — see [soft-keyboard.md](./soft-keyboard.md),
_avoidance_.

**The squeeze chain under that padding is load-bearing.** Whichever host
supplies it, the padding takes room away from the column above it, and every
link down to the scrollable content must be able to give height up: `min-h-0
shrink` on the panel (`share-kit.tsx`) and on each picker's `ScrollView`
alongside its `max-h-72` (`share-list-picker.tsx`, `share-tags-picker.tsx`). RN
children do not shrink by default, and a panel that cannot shrink does not clip
— it OVERFLOWS, painting its header outside its own background.

**The panel is bounded from the TOP, and it is a floor on the backdrop rather
than a cap on the panel.** `marginTop: insets.top + SHEET_GAP` on the panel
(`share-kit.tsx`), the same on both hosts. It replaces Android's `max-h-[85%]`,
which was the wrong shape twice over: a percentage of a box the keyboard has
already shrunk goes on taking its 15% out of the pickers' scroller at the moment
there is least of it (~50dp on a short phone — three rows down to two), and
being Android-only it left iOS unbounded. Neither is theoretical, because the
frame is a **ceiling and not a gap**: the panel is `shrink` inside `flex-1
justify-end`, so once its content exceeds the frame it fills the frame, rounded
top at `y=0`. A picker runs to ~484pt of content (16 + 36 header + 16 + 36 input

- 16 + 288 scroller + 16 + 44 button + 16) against ~407pt of frame on an
  SE-class phone with the keyboard up — a header under the status bar, on iOS,
  before Android ever lost its cap. A margin bounds by subtraction instead, so
  both hosts keep the same strip and neither reaches the hardware. It is a margin
  rather than frame padding because the backdrop `Pressable` is absolute against
  the frame's padding box, and padding would pull the dismiss target out from
  under the very gap it creates.

**The compose screen has no scroller and needs none** — it has no text field, so
the keyboard never reaches it — on the condition that nothing on it can grow
without bound. One thing could: the tags row's wrapping chips, now capped at
`MAX_TAG_CHIPS` with a `+N` remainder (`share-screen.tsx`). The row's
screen-reader `value` stays uncapped; the cap is a space constraint on a 375pt
row and a screen reader has none.

**The host view is full-screen, and that is what made a keyboard survivable at
all.** `ShareExtensionViewController` sizes its root view from
`ShareExtensionHeight` in the extension's Info.plist, pinning it at
`y = UIScreen.main.bounds.height - height`; with the key absent it uses the full
`screenBounds` instead. `app.config.ts` used to set `height: 520`, "sized for the
pickers" — and no amount of correct lifting fits a ~520pt picker above a ~340pt
keyboard inside a 520pt container. The key is now **omitted on purpose**. The
panel is bottom-anchored and paints its own background, so a full-screen
container looks identical while the keyboard is down and simply stops being the
ceiling when it is up. Nothing in JS may assume the surface's origin any more:
the lift is computed from the keyboard's own top edge, not from where the
container starts.

⚠ **"Full-screen" is a SIZE, and upstream applies it as a POSITION too — which
put the whole sheet 72pt below the bottom of the screen.** `configureRootView`'s
no-height branch is

```swift
rootView.autoresizingMask = [.flexibleWidth, .flexibleHeight]
frame = screenBounds                       // UIScreen.main.bounds
```

and `frame` is in the **superview's** coordinate space. The superview is the
extension view controller's own `view`, which the share presentation places
**72pt down from the top of the screen** and sizes to the remaining 802 — not at
the screen's origin. So a rect of the right size lands in the wrong place:
screen y 72 → 946 on an 874pt screen, with the bottom 72pt of the sheet, which
is where the Save button lives, off the display. Measured on iOS 26.5 with
`maestro hierarchy`, iPhone 17 and iPhone 17 Pro **identical**:

| node             | before              | after               |
| ---------------- | ------------------- | ------------------- |
| Safari (screen)  | `[0,0][402,874]`    | `[0,0][402,874]`    |
| `share-backdrop` | `[0,72][402,946]`   | `[0,72][402,874]`   |
| `Save`           | `[16,852][386,896]` | `[16,780][386,824]` |

`.flexibleHeight` does not save it — an autoresizing mask redistributes on a
_later_ superview resize, and there is no later resize, so the initial rect is
the final one. The fix is `frame = view.bounds`: fill the superview, which is
what the mask on the line above already says this view is for, and what the
library's own `initialViewHeight` initial prop (`self.view.bounds.height`, 802)
already tells JS the container is.

**It is a config plugin, `plugins/with-share-extension-root-view.js`, because
`ios/` is CNG output** — `addPbxGroup.js` re-copies
`ShareExtensionViewController.swift` out of `node_modules` on every prebuild, so
an edit there dies at the next `--clean` with a clean working tree throughout.
A `finalized` mod for the same reason as the build-settings plugin next door
(→ [expo-build.md](./expo-build.md), _ios share extension build settings_); it
rewrites the one branch, is idempotent, and **throws** if upstream rewords it
rather than silently leaving the sheet off-screen.

**Nothing in `features/share/` was wrong, and nothing there could have caught
it.** The panel is `shrink` inside a `flex-1 justify-end` frame and was
bottom-anchoring itself perfectly — to a box whose bottom edge was below the
display. `useSafeAreaInsets()` reports a clean 34 for such a view, because that
is what `UIView.safeAreaInsets` says; the Save button had its 16 + 34 of
clearance and all of it was off-screen. It is the same family as the two RN bugs
in _what an app-extension process breaks_ above — a plausible number, no error —
except that here the number is right and its **origin** is not. This is also why
`share-keyboard.ts`'s `panelBottom` (`Dimensions.get('screen').height`) was
wrong by the same 72 while it lasted: its doc comment asserts the RN root is
"flush with the bottom of the screen", which is exactly the assumption upstream
was breaking. That assertion is now true.

**The root must not paint, whatever its size.** Left to itself
`ShareExtensionViewController` fills that view with `.systemBackground` and
square corners. The sheet's four screens are not one height — compose and saved
are barely 280pt against the pickers' ~520 — and the difference showed as an
opaque slab of dead white above the header, which reads as a broken sheet rather
than as a short one. The plugin's `backgroundColor` takes an alpha
(`app.config.ts`, 0 there; note the Swift divides r/g/b by 255 but uses alpha
as-is), so the root is clear and `share-kit.tsx` draws its own rounded,
`bg-popover` panel inside it, under a `border-t` — the shape the Android half
always had, in the fill and edge every floating surface wears
([theme.md](./theme.md), _elevation_). What shows above it is the host app under
the system's own dimming.

That transparency has a consequence worth stating, and a full-screen root
sharpens it: **a clear RN root view still takes touches.** The unfilled region
looks like Safari and is not — and it is now the whole screen above the panel,
not the leftovers of a 520pt band — so the sheet puts a `share-backdrop`
`Pressable` under the panel on BOTH hosts, and that is the tap-outside-to-close
for everything around it. Untinted on iOS, where the system already dims,
`bg-black/40` on Android, whose activity is merely translucent. It is
`accessible={false}`, and `share-close` remains the announced way out.

**Neither the provider nor the insets come for free.** `SafeAreaView` has needed
an `RNCSafeAreaProvider` ancestor since react-native-safe-area-context v5 and
lays out with zero insets without one, so the sheet mounts its own provider —
seeded with `initialMetrics`, because `SafeAreaProvider` renders nothing until
its first measurement and the usual fallback, `initialWindowMetrics`, is null
here (it is `RCTKeyWindow()` again). Full derivation in
[safe-area.md](./safe-area.md), _safe area on native_.

**The rule this leaves behind:** anything the RN core computes from
`UIApplication`, the key window or the screen is suspect in this process, and it
will be wrong SILENTLY rather than throwing. `RCTKeyWindow()` and
`RCTSharedApplication()` (both nil-returning here) are the things to grep for
when a shared component behaves differently in the sheet than in the app — and
the grep pays out beyond RN core: safe-area-context's `initialWindowMetrics`
constant is `RCTKeyWindow()`, which is why it is null in the sheet and why the
provider above has to be seeded by hand.

### why not share the sqlite DB with the iOS extension

Putting `bracemark-data.db` in the App Group container so both processes open it
invites the `0xdead10cc` termination (iOS kills a suspended app holding a file
lock in a shared container) plus cross-process WAL edge cases. The extension
instead exchanges **atomic per-item JSON files** — no locks, no contention:

- `<app-group>/share/taxonomy.json` — written by the MAIN APP whenever
  lists/tags change (and on sign-in/out): `{ owner, lists, tags, linkCount, maxLinks }`,
  plaintext by design (bracemark-expo already stores content decrypted on device —
  see architecture.md). Lists are the merged system+user set in tree order,
  Trash excluded (saving into the deletion staging area is incoherent); tags in
  rank order. Every row carries its `rank` so the sheet can mint neighbour
  ranks for what it creates (below).
- `<app-group>/share/outbox/<linkId>.json` — one `ShareDraft` per Save, written
  by the EXTENSION:
  `{ id, owner, url, title?, listId, tagIds, newTags, newLists, sharedAt }`.
  The main app drains each through the normal write edge on launch/foreground
  and deletes the file only after the local write commits.
- `<app-group>/share/failed/<linkId>.json` — the **quarantine**: an outbox file
  the drain couldn't read, parked here rather than deleted (_the drain never
  destroys what it couldn't read_, below). Nothing reads it; sign-out clears it.

Both sides reach the container via expo-file-system's
`Paths.appleSharedContainers`; the App Group id is expo-share-extension's
default (`group.` + bundle id = `group.com.bracemark.app`).

### the draft is idempotent by construction

The link id (and any new list's/tag's id AND `rank`) is minted **in the
sheet** (`newId`) and travels with the draft everywhere — outbox file name,
sqlite row, server entity. It is minted **once per sheet, not once per Save
attempt**: the sheet's own retry after a failed Save is a retry like any other,
and Android's `applyShareDraft` writes the link row before the extraction title,
so a throw between them plus a freshly minted id would file the page twice. Any
path can retry (drain crash between item write and file delete, upload + later
drain, the user tapping Save again) and converge on the same entities
instead of duplicating or shuffling — the drain applies the draft's ranks
verbatim, so it re-writes byte-identical taxonomy entities to what the
extension may already have uploaded. Same reason the drain is a plain
re-`writeLink`: last write wins on identical content.

Minting a rank against the sheet's taxonomy (live on Android, a possibly-stale
snapshot on iOS) is safe because an equal-key **tie is an anticipated,
deterministically-resolved case** of the rank model, not a corruption: two
devices inserting at the same slot concurrently already mint equal keys, and
`compareRank` breaks the tie by id (shared `sync/rank.ts`) — a stale-snapshot
rank can do no worse.

**Rank is required on the draft and the snapshot** — there is no drain-side
fallback that computes one and no upload-side skip for entities missing one.
Those existed for files written by a build that predates sheet-minted ranks;
nothing has shipped, so no such file can exist, and the greenfield rule is to
tighten the schema in place rather than carry compatibility with a past that
never happened. A rank-free payload is corrupt and is rejected at the parse
boundary like any other malformed input — for the snapshot that means reading as
signed-out, which points the user at the app, and the app rewrites it
(`refreshShareTaxonomy`). Both pickers mint at **index 0** (the create-position
rule — [editors.md](./editors.md)), against the head of the group.

### the drain never destroys what it couldn't read

A tight schema and a deleting drain are safe **separately** and lethal
**together**, so `drainShareOutbox` pairs the strictness above with a
quarantine: a file it can't read — unreadable bytes or JSON the schema rejects —
moves to `share/failed/` instead of being deleted. It can't stay in the outbox
(it would be retried forever) and it can't be applied, but destroying it is the
one option that's unrecoverable.

The asymmetry that drives this: **the snapshot is a cache, the outbox draft is
sometimes the only copy.** `refreshShareTaxonomy` rebuilds a bad snapshot from
the store, so discarding one costs a confusing sheet and self-heals. A draft has
no such source — the best-effort upload is what would have made a second copy,
and it fails exactly when the user was offline. So the rule is: **version what
you can't reconstruct, discard what you can, and never delete what you couldn't
read.** Only the third clause needs code here.

What makes this more than theory is that a parked file **outlives the code that
wrote it**. The app and the extension ship in one bundle and update atomically,
so two builds never run at once — but an outbox file written before an update is
read by the drain after it, and that is the one skew this design has. It is also
the direction that matters: only "new code reads old file" can happen, never the
reverse. The exposed user is the one the share sheet is FOR — share, never open
the app, auto-update lands. Quarantining turns that from a silently vanished
link into a recoverable file.

Nothing reads `share/failed/` today; there is deliberately no version tag and no
migration path, because a version field only pays for itself if you write the
second parser, and the quarantine keeps the option open **without** committing to
that. Sign-out clears it with everything else (`clearShareData` deletes the whole
`share/` subtree rather than naming artifacts, so a future addition can't be
missed).

### a draft belongs to the account that opened the sheet

The snapshot names the account it was built for (`owner`, the signed-in
username), and the sheet stamps that name on every draft it mints. Three places
land a draft, and each one lands it **only under that same account**:

| where                                | when the owner is not the signed-in account                           |
| ------------------------------------ | --------------------------------------------------------------------- |
| Save (`saveSharedDraft`)             | writes nothing and answers `'account-changed'` — before the cap check |
| the iOS upload (`uploadQueuedDraft`) | sends nothing; the outbox file stays for the drain to decide          |
| the drain (`drainShareOutbox`)       | deletes the file and lands nothing from it                            |

Before the stamp, a draft named no account, and whoever was signed in when it
landed became its owner. Two schedules made that a crossing. A sheet opened
under one account and saved after the user switched the app to another wrote
the first account's choice into the second's library. And because the iOS
share extension is its own process, nothing orders its outbox write after the
sign-out wipe: a write that lands after the wipe survives it, and the next
account's drain used to apply it. Sign-out still deletes the whole `share/`
subtree. The owner check covers what the wipe cannot see.

**Save checks against the current state, not the one the sheet opened on.**
iOS has no session of its own in that process, so it reads the snapshot again:
sign-out deletes it, and the next account's first refresh rewrites it under its
own name. Android reads `getSession()`. Either way, a mismatch or no session at
all is `'account-changed'`. Account before cap: another account's full library
is no reason to tell this user to free up room.

**A mismatched draft is deleted, and that is not a breach of _the drain never
destroys what it couldn't read_.** That rule is about files the drain cannot
read, because such a file may be the only copy of the user's share. A
mismatched draft is readable, and it is the other account's. The wipe existed to
remove exactly this file. Quarantining it in `failed/` would keep one account's
URL on a device now signed in to someone else.

**Same account, any sign-in: it lands.** A draft saved offline, or while the
session was expired, still lands after the user signs back in to the same
account. That sign-in is a resume and keeps the library
([sessions.md](./sessions.md)), and that offline share is the work the outbox
exists to keep. So the binding is the username alone, with no session
generation. A username is a stable identity here because the server never
releases one: deleting an account tombstones it ([account.md](./account.md)). If handles are ever released ([data-lifecycle.md](./data-lifecycle.md), _deferred_) or made editable ([account.md](./account.md)), this binding has to move to an id that neither a re-registration nor a rename can change. A rename alone would make the drain delete that account's own pending drafts.

**A refresh that started under one account never writes its snapshot after the
switch.** `refreshShareTaxonomy` takes the username before its reads and checks
the session again after them, with nothing awaited between that check and the
write. `clearSession` and `saveSession` update the in-memory session before the
wipe and before the next account's first refresh. Without the check, a pass
caught in a sign-out would write the old account's snapshot back after the wipe
deleted it, and every share made from it would be refused.

**What the binding does not close.** It decides where a draft lands, not when
one is written, so each of these is still possible and none of them crosses an
account:

- **A share written after the wipe still shows ✓.** The sheet saved its file,
  and the next drain deletes it (another account) or the next sign-in's wipe
  removes it (the same account, with nothing persisted). The user was told it
  saved, and it never lands.
- **A Save that reads the snapshot mid-rewrite answers `'account-changed'`.**
  expo-file-system writes a string in place (`atomically: false`), so the
  re-read can see a part-written file, which parses as nothing. Nothing is
  written, and sharing again works. The message is wrong, and nothing is lost.
  Before the owner check this re-read was only the cap check, which fails open.
- **An old account's draft caught mid-write is quarantined, not deleted.** The
  same in-place write: an unreadable file goes to `failed/` under the drain's
  rule, because the drain cannot read whose it is. It is never applied, and it
  stays on the device until the new account signs out.
- **The share extension's requests read the bearer token per request.** The
  upload checks the mirrored account once, then `auth-api-client.ts` reads
  `getSession()` for every request it sends. A second share saved in the same
  extension process under another account, while the first is still uploading,
  replaces that session, and the first upload's remaining requests carry the
  second account's token for blobs encrypted under the first's key. It needs a
  full sign-out and sign-in between two shares within one upload's life, in a
  process iOS normally suspends. It predates the binding.

The snapshot's `owner` replaced a `sessionPresent` boolean, which told the
sheet that some account was signed in but not which. Like `rank`, the field is
required with no back-compat slack. A snapshot without it reads as signed out
(the app rewrites it), and a draft without it is quarantined. The jest pins are
in `share-store.spec.ts` (_the draft's account_, the drain cases,
`refreshShareTaxonomy`) and `share-screen.spec.tsx`. No device case drives an
account switch with the sheet open. The checks are plain comparisons on both
sides of the process boundary, and the existing `SHARE-*` cases exercise the
stamp on every iOS save.

### the sheet's shape — four screens, one specimen

The sheet floats over Safari for about three seconds, and the traffic through it
is lopsided: **the 90% path is share → Save**; the list and the tags are the
10%. The layout is built around that, and around one object.

**The page is the subject.** `share-specimen.tsx` draws the shared URL the way
the library will draw it — the row's own 64x40 slot carrying a monogram, the
title, the address ([brand-assets.md](./brand-assets.md#the-mark) has why that
slot is 16:10 and what the 12px cut now reads against) — and it
holds the top of the sheet from the loading state through the confirmation. It is
the RN port of the browser extension's `PageSpecimen`, deliberately: that popup
already learned the lesson this sheet hadn't. A compose screen followed by a
separate "✓ Saved to Bracemark" screen reads as submitting a form and being
handed a receipt — two screens with nothing visibly in common. Here the save
happens **to** the object: the controls beneath it change, the specimen does not
move, and **its corner comes off**. That fold is the part of the confirmation that
happens to the OBJECT — the saved phase also prints "Saved to <list>" and swaps
the controls, so the words carry the state — and it is the meaning the mark already
carries on the extension's tile: square is unsaved, cut is saved
([brand-assets.md](./brand-assets.md#the-mark)), not a new one.

The two pickers are the exception, and a deliberate one: they replace the
specimen rather than sit under it. They are screens precisely because the tree
and the full-width tag rows need the height (below), and 40px of tile plus its gap is a
sixth of what the list has to work with. The thread the user is holding is the
one they just tapped — "choose a list" — not the page, which is still there when
they come back, unmoved.

The tile is **always the monogram**. Web's chain is extracted image → the live
tab's favicon → HostMonogram; the sheet has neither of the first two and must
not go looking (it never fetches the page, and the iOS extension must stay off
the app's sqlite, where a cached favicon lives). The deterministic tile is the
whole chain — and it is the same tile the library draws for that host, so "same
site, same mark" holds across the boundary. It FILLS the slot rather than sitting
in it: with no favicon and no image to fall back from, the mark is the only
identity this surface will ever have, so it gets the whole rectangle — and the
corner cut then always lands on a filled field. Web reaches the same result
through `HostMonogram`'s `ratio` prop; here it is just the View's background.

**The choices are disclosed, not spread out.** The compose screen carries two
rows — destination and tags — each showing the current answer and opening a
screen with room to change it. A destination is one value; a tag set is bounded
by what the user picked. The pickers were previously a `max-h-40` peephole
nested inside the sheet's own ScrollView plus a blind "New list…" field, which
gave the 10% path most of a 520pt panel and still had nowhere to put a tree.
As screens they get the height, and they borrow the app's own picker rules and
row presentation line for line (`components/links/list-command.tsx`,
`tags-command.tsx`): one input that
filters as you type and doubles as the new entity's name field, ancestor paths on
filtered rows, an explicit `Create "…"` affordance suppressed on an exact
case-insensitive match. Someone who has picked a list in the app should not have
to learn a second picker here.

So the four screens are **compose → (choose list | add tags) → saved**, switched
by local state rather than a router — the extension bundle has no business
carrying one. Three rules hold them together:

- **The header is constant** (`ShareHeader`, `share-kit.tsx`) and the same height
  on all four screens, so nothing under it ever shifts as the sheet switches. It
  carries the **brand lockup** — this is the one surface in the product that
  floats over another app and has no other carrier — plus a close control, which
  is not decoration: the system's swipe-down and the backdrop are both ways out
  with nothing on screen to announce them, so this is the one way out that is
  visible on every screen at every height — which is also why its 36pt box carries
  `hitSlop={6}`. It is the one control in the product where a near-miss strands
  the user inside somebody else's app rather than merely annoying them
  ([accessibility.md](./accessibility.md), _a 36dp box is not a 44pt target_). The lockup's row is
  the full width of the header — it places that control with `ml-auto`, so a
  `flex-row` PARENT collapses it to its content and strands the control against
  the wordmark; both rails put the lockup in a column for the same reason
  (`features/{links,settings}/sidebar.tsx`).
- **The pickers hold the system's swipe off; the compose screen does not.** The
  host presents the share extension in a sheet of its own, and a downward drag
  on it belongs to that sheet, on every screen: a short one moves the sheet and
  lets it settle back — the keyboard, if up, leaves and returns to the
  still-focused field — and a long one dismisses it, taking the unsaved share
  with it. Driven by hand on an iPhone from the pickers' lists, keyboard up and
  down; on the simulator a 13pt downward drag on a compose row is already enough
  to start it (the host's `viewWillDisappear` appearance action arrives in the
  extension's log, 10pt is still a press). On a picker that is an accident
  waiting for anyone who pulls a list already at its top: "down" there means
  "scroll", and nothing in JS sees the gesture or can veto it. So the pickers
  pass `holdSwipe` to `ShareSheet`, which mounts `ShareSwipeGuard`
  (`share-swipe-guard.tsx`). It renders nothing: mounted, it calls `setHeld(true)`
  on our own module (`BracemarkShareSwipeGuard`, `modules/bracemark-share/ios`),
  which posts a notification; `ShareExtensionViewController` observes it and sets
  `isModalInPresentation` on itself, and unmounting gives it back. The module
  cannot reach that controller directly — it is `expo-share-extension`'s class,
  compiled into the extension target, and there is no `UIApplication.shared` to
  walk down from — so the observer is patched into the controller by
  `plugins/with-share-extension-swipe-hold.js`, beside the `close` observer the
  library already carries, for the reason the root-view plugin exists. The
  compose screen passes nothing, on purpose: swiping a share sheet away from its
  first screen is the platform's own gesture — and it is a CANCEL, which leaves
  the user on the system share sheet they came through, where `share-close`
  completes the request and returns them to the page. Driven by hand on an
  iPhone 12 (iOS 26.5): with a picker up, a long pull from the top of its list
  makes the sheet resist and stay, and back on the compose screen the same pull
  still closes it. A missing observer and a guard that never lets go are both silent
  everywhere else, so two checks stand on that chain. Its STRINGS — the module's
  name and function, the notification, its `userInfo` key, the class autolinking
  registers, the plugin's anchor in the installed library — are held to each
  other by `share-swipe-hold-wiring.spec.ts` and `share-swipe-guard.spec.tsx`
  ([testing.md](./testing.md)). Its BEHAVIOUR is `SHARE-IOS-003`
  ([e2e.md](./e2e.md), _gestures and waits the runner performs_): the simulator
  honours the flag too, so one scripted flick must leave each picker standing
  and then take the compose screen away. What neither reaches is a thumb on
  hardware — re-drive that one gesture on both screens, on a phone, after
  touching the module, the plugin or `holdSwipe`.
- ⚠ **The share extension has almost no memory to spare, and exceeding it looks
  like nothing at all.** iOS caps an app extension's memory per process and
  kills it at the cap — no crash report, no error in Metro or Xcode, the sheet
  simply gone — and the simulator enforces no such cap, so everything below
  passes there. The guard above was first written as a sizeless Expo native
  VIEW that found the controller through its own responder chain, which needed
  no plugin. On the simulator it worked. On an iPhone 12 (iOS 26.5, dev build)
  the extension died the moment either picker mounted. Measured: on the
  simulator the extension's footprint is 170MB on the compose screen, a picker
  adds 4MB, and a picker carrying that one native view adds 18MB — the first
  Expo native view in this process costs ~14MB. On the phone, a probe that held
  2MB more every 200ms over an open picker was last heard from at 12MB, so a dev
  build has roughly 16MB of headroom over the compose screen. **Nothing on this
  path may mount a native view from an Expo module, or otherwise spend memory in
  the tens of megabytes**; a module FUNCTION costs nothing measurable, which is
  why the guard is one.

  **Most of that 170MB is the dev build, not the sheet.** The same screens,
  release build against dev build, read off the simulator's own process with
  `footprint` (`pgrep -f BracemarkShareExtension.appex` finds it — a simulator
  process is a host process), iOS 26.5:

  |                                | dev build   | release build |
  | ------------------------------ | ----------- | ------------- |
  | compose                        | 166–171 MiB | 59–64 MiB     |
  | list picker up                 | 174–176 MiB | 65.7–65.9 MiB |
  | after two laps of both pickers | 180 MiB     | 68 MiB        |

  The ~105 MiB between them is one line of the breakdown: `MALLOC_SMALL` is 105
  MiB in the dev build and 15 in release, which is the bundle arriving from Metro
  as source and being parsed in-process, plus the dev tooling, where a release
  build maps Hermes bytecode from a file. What a release build still pays at
  compose is mostly not JS either: 17 MiB of dyld private memory and 16 of
  `__DATA`/`__DATA_CONST` — the cost of the binary the share extension target
  links, spent before a line of the bundle runs — against 15 of malloc and 10 of
  untagged VM (Hermes's heap, most likely). So the lever on the release
  footprint is what that target LINKS (`excludedPackages`, `app.config.ts`),
  more than anything in `features/share/`.

  Two things those numbers do not say. They are not the phone's: the simulator
  enforces no cap and its footprint is not a device's (the dev build that reads
  170MB here still had its ~16MB of headroom on the iPhone 12), so **how much
  room a release build has on hardware is still unmeasured** —
  `os_proc_available_memory()`, read inside the extension with a picker up, is
  the call that answers it, and `SHARE-IOS-MEMORY-RELEASE-001`
  (`e2e/mobile/RELEASE.md`) is the check that stands in until something reads
  it. And the dev build's figures do not repeat: its first picker costs anywhere
  from 3 to 10 MiB, and it never gives a lap back — which is why no e2e case
  asserts a footprint ([e2e.md](./e2e.md), _what e2e may not assert_). Two laps
  cost the simulator's dev build ~14 MiB, which is about the headroom the phone's
  had — so a DEV build that dies on a phone after a few laps through the pickers
  may be this paragraph rather than a regression. Check a release build before
  chasing it.

- **The two disclosure rows say what they are to a screen reader**, even though
  they carry no visible label: `ShareRow` takes a `label` + `value` and announces
  "List: Reading" / "Tags: alpha, beta". Dropping a word of type from a 520pt
  sheet is a visual decision, and it does not extend to dropping the semantics —
  without this the row reads as a bare value with no hint of what it changes.
  ([accessibility.md](./accessibility.md) collects the cross-cutting rules; the
  sheet's save failure uses the `ErrorText` carrier described there.)
- **One primary button in the whole sheet**, and it is Save. Every other button
  on every screen is an outline.
- **The verb is "Save" the whole way through** — button, progress ("Saving…"),
  confirmation ("Saved to _My List_") — matching the extension popup and the
  app's own add screen. The confirmation names the DESTINATION because "Saved"
  alone is half an answer in an app whose organising idea is lists.

### what the sheet does and doesn't do

- **Title**: comes from the share payload only — Android `EXTRA_SUBJECT`, iOS
  the preprocessing JS (`document.title` captured in Safari's own context, no
  network). A share-payload title is NOT a deliberate user title, so it seeds
  the provisional `extraction.title` (via `writeExtraction`), never
  `customTitle` — the same rule as bulk import (entities.ts). The sheet **never
  fetches the page**; image/screenshot/page-copy fill in later through the
  normal extraction pipeline in the main app.
- **URL**: Android's `EXTRA_TEXT` sometimes wraps the URL in prose (Chrome),
  so the first http(s) URL is extracted from the text; normalized with
  shared's `normalizeUrl` before storing.
- **Locks**: the sheet's pickers filter **only Trash** — the same rule as every
  editor picker (editors.md, "Locked and hidden lists stay pickable"): a lock
  gates a list's CONTENTS (reading already-decrypted data), never its use as a
  destination, and `hideList` is a pure sidebar declutter that no picker
  prunes. So `computeCoverage` and the lock model stay out of the share
  surface entirely — the taxonomy snapshot doesn't read locks at all.
- **Theme**: the sheet honors the app's light/dark preference, and it reads it
  from a **file mirror** rather than from settings — the App Group container on
  iOS, the document directory on Android — written by the app's `ThemeProvider`
  as it applies its own. Same argument as the taxonomy snapshot, one surface
  over: the preference lives in encrypted synced settings plus a sqlite row, and
  the extension may open neither. The read is synchronous and applied during the
  sheet's first render (an effect would paint the OS theme and flip), it carries
  the `ThemeState` so `custom` resolves against the clock at open time, and every
  failure path lands on `system`. Full rationale — including the ownership claim
  that stops an Android share from re-theming the app it shares a process with —
  in [theme.md](./theme.md), _the share sheet_.
- **New tags AND new lists** — the sheet mints both, matching the web editors
  (`TagsField`'s always-on mint, `ListSelect`'s `allowCreate` — editors.md) and
  their rules: a typed name that exactly matches an existing list/tag
  (case-insensitive) reuses it instead of minting; a new list is **top-level
  only** (`parentId` pinned null at apply — create now, reparent later in
  Settings → Lists). Both ride the draft as `{ id, name, rank }` — id and rank
  minted in the sheet (rank from the taxonomy's neighbour ranks: prepend before
  the first root list for a list and before the first tag for a tag, matching
  web's create-at-index-0; several new tags chain off each other, so they
  stack newest-first), so the upload can push complete entities and
  the drain re-writes the identical ones (see _the draft is idempotent_,
  above). Both pickers draw a pending entity where that rank will put it — the
  top rows, above the snapshot's — so the sheet shows the order the app will
  after Save. A new list exists only as the share's destination: creating selects
  it, and selecting another list discards the pending create.
- **Duplicates**: not detected in the sheet (iOS can't see the DB; a stale
  snapshot would lie). Save anyway; dedup is the apply-side's concern.
- **The plan's link cap**: **checked on both platforms**, off different sources —
  and that split is the process boundary, not a difference in the rule. Every
  create surface refuses the save at the cap and shows the upgrade banner instead
  of the form ([editors.md](./editors.md)), and since the cap is client-enforced
  (docs/iap.md, _enforcement_) these gates ARE the wall — nothing behind them
  counts links.

  **The sheet obeys that rule literally: the banner replaces the form.** It
  reads `linkCount`/`maxLinks` off the taxonomy it already loaded — the same two
  numbers `isAtLinkCap` uses, on both platforms — so the refusal lands before
  the user files a link that was never going to be saved. There is no upgrade
  CTA on it, because neither host can route into the app's subscription screen
  (Android's `BracemarkShare` module exposes `close()` and nothing else); the
  banner's own sentence is the direction.

  `saveSharedDraft` still returns `'quota'`, and the sheet still handles it, as
  the backstop for the count moving underneath the gate — Android re-counts
  sqlite live inside the save, and an iOS snapshot can be a run of shares old.

  Android's share activity runs in the app's process, so `isAtLinkCap`
  (expo-react's `data/share-store.ts`) counts `links/` rows the trash-INCLUSIVE
  way against the cached plan's `maxLinks`, live off sqlite.

  iOS reads both numbers off the **taxonomy snapshot**, which now carries
  `linkCount` + `maxLinks` beside the pickers' lists and tags. It has to: the
  count lives in the sqlite the extension must not open, and so does the cached
  plan (`subscription-store.ts` goes through `getDb()`). The cost is one indexed
  `countLinks()` per snapshot write, and the write cadence was already right —
  `ShareBridge` refreshes on `localWriteNonce`, which `requestSync()` bumps on
  every local write, so the snapshot is rewritten per save rather than per
  taxonomy change. The refusal happens BEFORE the outbox file is written, which
  matters because everything downstream of that file is built never to drop it.

  Both fail **OPEN** wherever the answer is unknowable — no cached status on
  Android, no snapshot or a pre-cap-fields snapshot on iOS. Guessing `free` would
  tell a paying customer their library is full, and there is no longer a server
  gate behind the guess to correct it. The residual gap is a RUN of iOS shares
  taken without reopening the app: they are all judged against the count as of
  the first one, and the drain + refresh on next foreground re-syncs it.

- **No session** (cold share before first sign-in): the sheet shows "Sign in to
  save links", and says why — each link is encrypted with a key the password
  unlocks, so there is nothing the sheet could do without it — instead of
  hanging or crashing. Snapshot absent / `owner: null` on iOS,
  `getSession() === null` on Android. It and the no-link state are shaped like
  the links pane's `EmptyState` (a mark, a title, a sentence that says what to do
  next), because they are the same kind of moment.
- **Sign-out hygiene**: clearing account data also deletes the snapshot and
  outbox (clear-data.ts), same reasoning as the session-store install
  sentinel's Keychain-ghost note. The wipe is not the only guard: a draft is
  landed only under the account that owns it, so one the wipe missed lands
  nowhere (_a draft belongs to the account that opened the sheet_).
- **The account changed while the sheet was open**: Save answers
  `'account-changed'`, writes nothing, and the sheet puts "You signed out of Bracemark, or into another account, after this opened. Close this and share the link again." in its error line.
  A retry would refuse again, because the lists and tags on screen are the old
  account's; reopening the sheet reads the new one.

### the write edge it lands on

`@stxapps/expo-react` `data/mutations.ts` — the port of web-react's local
write edge (see there for the canonical semantics): decrypted blob into
`items` **and** the pending op enqueued in ONE drizzle transaction, engine
drains the queue on the next sync cycle. The share flow needs `writeLink`,
`writeTag` (new tags), and `writeExtraction` (title seed); the other siblings
arrive with their features.

**The sheet dismisses fast; sync is never awaited in-sheet.** The durable
commit is the local write (the pending op enqueued in the same transaction on
Android, the outbox file on iOS) — NOT the sync completing. So Save is always
`write → the fold → close()`; any sync/upload is fired **best-effort,
un-awaited**.
Never hold the sheet on a "syncing…" spinner: the user shared and wants back to
the caller, and delivery is guaranteed by the durable record + next-open drain,
not by the in-sheet kick landing.

- **Android Save** = mutations writes, then an inline sync kick, un-awaited —
  one entity, sub-second, so it usually lands while the process is alive.
  **Caveat: the ShareActivity's process may have been spawned just for the
  share** (main app not running); once the activity `finish()`es and nothing
  else is foreground, the process is a cached process eligible for reap, which
  cancels an in-flight sync. So (a) launch the kick on an **application/process
  scope, not the Activity scope**, or `finish()` cancels it outright; and (b)
  treat even that as best-effort — a process-scope coroutine still dies on
  reap. Delivery is guaranteed by the **pending op + next-open drain + the
  background-task cadence**, never by the inline kick. If a hard "on the server
  before the user looks elsewhere" guarantee is ever needed, the right tool is
  **WorkManager** (survives process death, network-constrained, retrying) — an
  enhancement, since the pending op already makes it lossless. (WIRED: the kick
  lives in `saveSharedDraft` itself — the sheet passes the app's api client in,
  and the un-awaited `runIncrementalSync` promise runs on the app-level React
  host's JS runtime, which the activity's `finish()` doesn't cancel; that IS the
  process scope in RN terms.) Between the write and that kick, Save leaves a
  **handoff marker** for the main app — _the Android handoff_, below.
- **iOS Save** = outbox write + best-effort upload kick + the fold +
  `close()`. Down-sync happens on next launch/foreground drain (`ShareBridge`);
  an opportunistic BGAppRefresh backstop (expo-background-task) remains a
  possible enhancement, less pressing now that the upload gives cross-device
  freshness at share time.

**A landed share counts toward the app-store review prompt.** A share is a
save, so it is counted toward the ten saves that earn the ask — in
`applyShareDraft`, because that is where both platforms' shares land in the
app's own process: Android's Save calls it directly, and the iOS drain calls it
for each outbox draft. The iOS share extension can't count its own saves (the
count is a row in the sqlite it must not open), and neither shell ever asks:
the ask comes on the next save in the app
([expo-dependencies.md](./expo-dependencies.md), _expo-store-review_). The count
is the one thing `applyShareDraft` does that is not idempotent — a draft applied
twice counts two saves — and that is left alone: it can only bring an ask one
save forward, where a "count only a new link" guard would miss shares whose
upload a sync pull landed before the drain.

### the main app's half — ShareBridge

`ShareBridge` (bracemark-expo `components/share-bridge.tsx`) is a renderless
component mounted inside `<ExtractionProvider>` — and so inside `<SyncProvider>`
— in `(app)/_layout`, since it reads both `useSync` and `useExtraction`. It is
the app-side pump for both App Group artifacts:

- **inbound**: `drainShareOutbox()` on mount and on every return to foreground
  — **once the store is ready**, below;
  a drain that landed drafts calls `requestSync()` so the pending ops push
  immediately and the read edge shows the user their own share without a
  refresh pill, and hands the landed links to `extractNow` — a share is a save
  gesture made on this device, so its page fetch needs no opt-in
  ([link-extraction.md](./link-extraction.md), _the stance_). The same pass
  collects what the Android share activity handed off (`takeShareHandoffs()`),
  into the same list and the same two kicks — _the Android handoff_, below.
- **outbound**: `refreshShareTaxonomy()` after every drain (a draft can mint
  new lists/tags), after every completed sync cycle (`lastSyncAt` — a pull may
  have changed lists/tags), and on every local edit (`localWriteNonce`). Locks
  never enter the snapshot (the pickers filter only Trash — see _Locks_ above),
  so lock edits are no concern here.

The drain and the snapshot are platform no-ops on Android, the handoff one on
iOS, and all three are failure-tolerant — a missed pass self-heals on the next
signal.

**The drain waits for the first sync; the snapshot does not.** `ShareBridge` is
mounted above `InitialSyncGate`, so it is live for the whole of a first sync,
and a share can arrive during one: the session is mirrored at sign-in, so the
sheet works while the library is still downloading. Drained then, a draft lands
with everything the drain hands on switched off. `extractNow` returns at once
until the store is ready, and by the time it would not the outbox is empty and
nothing offers the link again — at extraction mode `saves`, a share that never
gets its page fetch. The sync kick is declined
([local-first-sync.md](./local-first-sync.md), _two tabs, one queue_, the expo
paragraph — which is also what it cost when it was not). And the draft's list is
checked against a store that is still filling. So the drain is skipped until
`storeStatus` is `ready`, with `ready` a dependency of the effect: the pass that
was skipped runs when the gate opens, with no foreground needed. The drafts
lose nothing by waiting — the outbox is the durable record, and the share
extension's own upload has usually put them on the server already. The **snapshot** is still
written on every pass, ready or not: its existence is how the sheet knows there
is a session at all (_the shape_), so holding it back would turn the sheet away
for the length of a first sync.

**A first sync is the long case of "not ready", not the common one.**
`storeStatus` is `checking` at the start of every launch, for as long as one
read of the bookkeeping row takes, and the mount pass runs inside that window —
closed over the `extractNow` of that first render, which returns at once. A
drain there hands the whole outbox to it: the drain is synchronous sqlite under
its `await`s, so it has finished before the render that turns `ready` can
replace the closure. That is every share found by a cold start, which is how a
share is usually found — landed, synced, and at extraction mode `saves` left
with its provisional title and no image, with nothing reporting it. The same
line holds both windows, and `share-bridge.spec.tsx` runs its case once per
status the gate is closed in. On a device it is `SHARE-EXTRACT-IOS-001`: a page
shared from Safari with the app killed, then a cold start — which, with the
drain let through unready, leaves the "links without a preview" prompt up for
the link it just drained ([e2e.md](./e2e.md), _across a real share boundary_).

**The Android handoff.** Android has no draft to hold back: its Save writes
through the write edge whenever it happens, first sync or not. That write is
safe for the reason above, and its inline kick is declined the same way. What
it has no way to do is fetch the page. `extractNow` belongs to
`<ExtractionProvider>`, which the share activity does not mount — it renders
`ShareRoot` with no providers — and its process may be reaped seconds after
Save, mid-fetch. So until the handoff existed nothing told the main app which
links had arrived by share, and at extraction mode `saves` an Android share
never got its page fetch: not a race, every one of them. The iOS drain had been
handing its links on all along, because the outbox file is that record.

So Android's Save leaves one: a small file per link under the app's document
directory (`share/handoff/<link id>`, beside the theme mirror), written
**after** the link's write commits — a marker must only ever name a link that
is in the store, since the main app's pass can run between two awaits of a
save. `ShareBridge` collects them beside the drain, under the same ready-store
rule, and each is deleted as it is read. A file and not memory, because the
process that took the share is often not the one the user comes back to; a file
and not a table, because it is the per-item shape the outbox already has and
there is nothing to migrate. The marker is a hint and never the only copy of
anything, so an unreadable one is dropped rather than quarantined, and one that
fails to land costs that share its page fetch and nothing else. Sign-out removes
the directory (`clearShareData`) — the ids are the account's.
`SHARE-EXTRACT-ANDROID-001` holds the whole path on a device: a share taken with
the app killed, under a title the page does not have, and the row takes the
page's own once the app is opened ([e2e.md](./e2e.md), _across a real share
boundary_).

The handoff also gets the sync kick the drain gets, and on Android that is not
redundant. The share activity's own kick is best-effort — declined during a
first sync, lost with a reaped process, failed when the share was made offline —
and nothing else in the app pushes on a return to the foreground, so a share
made offline beside a running app otherwise waited for the next edit.

### immediate upload from the iOS extension

**The outbox is the record of truth; the upload is a best-effort fast path on
top of it — not a replacement.** The extension builds the entity, writes the
outbox file (durable, always), and _then_ best-effort encrypts + PUTs it:

```
tap Save →
  mint id, build ShareDraft →
  write outbox/<id>.json         ← durable, always happens
  best-effort: encrypt + PUT     ← may fail (offline, key read, link error)
  the fold + close()
```

Keeping the outbox even when the upload "works" is what makes the share
**lossless**: an offline or failed PUT would otherwise drop the link, so the
outbox is always the thing the main app drains on next open (local write +
upload) as the fallback. It's safe to have both fire because the design is
**idempotent by id** (minted in the sheet): extension uploads → main app later
drains the same outbox item → re-uploads under the same id → last-write-wins,
no duplicate.

**What the upload actually buys — and what it doesn't.** For the _sharing
device itself_ it buys nothing the next-open drain wouldn't: the phone
populates its own local store on next open regardless (down-sync pulls back its
own upload, or the outbox drain writes it). The upload's real payoff is
**cross-device / web freshness** — your laptop and bracemark-web see the link
without waiting for you to reopen the phone app. It stays contained and
additive: if the upload path ever misbehaves, deleting the kick reverts to the
still-correct outbox + next-open story.

**The upload runs in RN, because the runtime is already warm.** The sheet is
RN, so at Add time the JS instance is up and the upload is just more work in a
runtime already paid for — reusing the v1 frame (`blob.ts`), the typed sync
endpoint contract (`@stxapps/shared`), and the api client, instead of forking
AES framing + HTTP + endpoint types into Swift for zero latency benefit. (The
upload's language follows the sheet's language: if the sheet were ever forked
to native SwiftUI for cold-start reasons — see below — the upload would go
native with it, on CryptoKit + the v1 frame BracemarkFileCrypto already produces.)

**How the session crosses the process boundary.** expo-secure-store doesn't
expose Keychain access groups, so the **BracemarkSharedKeychain** native module
(`packages/expo-crypto`, in the `BracemarkCrypto` pod alongside BracemarkFileCrypto)
carries a shared-Keychain trio (`set/get/deleteSharedKeychainItem`,
`lib/shared-keychain.ts` — iOS-only, registered under `apple.modules` with no
Kotlin counterpart; the wrappers degrade to "item absent" elsewhere). The access group is the **App
Group id itself** (`group.com.bracemark.app`): iOS accepts App Group ids as keychain
access groups, so the entitlement expo-share-extension already writes into both
targets covers it — no keychain-sharing entitlement, no team-id prefix.
session-store **mirrors** the serialized session into that group on every
`saveSession`, and removes it on `clearSession` and the fresh-install wipe (the
mirror is a Keychain ghost too). The mirror is a copy, never the source of
truth: only the extension reads it, via `loadSharedSession()`, which also
hydrates the in-memory session mirror so the api client's synchronous
`getSession()` works in a process that runs no AuthProvider. Every mirror
write/delete is best-effort — a Keychain hiccup must not fail sign-in/out; a
missing mirror just means no fast-path upload (the drain still delivers). The
mirror carries the session's STATE, and the share extension reads it instead of
a clock: while it is `expired` (`uploadQueuedDraft`, `data/share-store.ts`) no
upload is attempted — the outbox file waits for the app's drain and the resume.
Nor is one attempted when the mirror names a different account than the
draft's `owner`. The mirror is read after the outbox write, so it can already
be the next account's (_a draft belongs to the account that opened the sheet_).
The share extension never acts on a 401 itself: [sessions.md](./sessions.md),
_who acts on a 401_. On Android, where the share activity runs in the app
process, an expired session skips the inline sync kick the same way.

**What the upload sends.** `uploadShareDraft` (`data/share-upload.ts`) builds
the **complete entity set from the draft alone** — the new lists/tags (carrying
the sheet-minted `rank` — see _the draft is idempotent_ for why a stale-snapshot
rank is only a tie), then the **link**, then the provisional
**extraction title** when the payload carried one — encrypts each with the v1
frame, and pushes sign → PUT → commit — the same three round trips as one
engine put-chunk, minus the store bookkeeping (the extension must never open
the app's sqlite). Uploading the taxonomy entities is what makes the upload's
payoff whole: another device sees the link **in its new list, with its new tag
chips**, without waiting for the phone app to be reopened. Since rank is
required on the draft, there is no partial-entity case here — the set is always
complete. Failures skip the commit
(no partial entity set) and are swallowed: no retry wrapper either — the
extension process lives ~a second past the ✓, so the durable outbox IS the
retry.

Prebuild verification: the extension target gets its own `use_native_modules!`
pass in the generated Podfile (expo-share-extension's `withPodfile`), so
community RN modules link there as they do in the app — that is what covers
`react-native-svg` (the lockup's mark) and `react-native-safe-area-context` (the
sheet's bottom inset), neither of which is in `excludedPackages`. Confirm
`react-native-quick-crypto` links into the
extension target — if it doesn't, the fallback is **not** "go full Swift" but
call **BracemarkFileCrypto** (your own autolinked module — the `BracemarkCrypto` pod
links anyway for BracemarkSharedKeychain) for the AES, staying in the RN path. The entity blobs are
KB-sized (no Argon2, key pre-derived, far under the ~120MB cap).

⚠ **A pod the two targets share has to resolve to the same subspecs in both, or
every Archive fails — and nothing short of an Archive says so.** When the
extension's set differs from the app's, CocoaPods builds the pod twice (a
`<Pod>-Core` target beside `<Pod>`), and only an install-action build — Xcode
Archive, `xcodebuild archive` — copies both copies' resource bundles into one
`UninstalledProducts` directory: `error: Multiple commands produce
'…/SDWebImage.bundle'`. A Release _build_ keeps them apart, so the simulator, a
device run and the e2e Release builds all pass. That is how
`expo-image-manipulator` sat in the extension unnoticed: it pulls
`SDWebImageWebPCoder` → `SDWebImage/Core`, while the app takes the full
`SDWebImage` through `expo-image` (already excluded here). It is now in
`excludedPackages` too — the sheet never calls it; its bundle names no
`ImageManipulator` module — which leaves `SDWebImage` to the app alone. After
changing `excludedPackages` or adding a native module, prebuild and check
`ls "ios/Pods/Target Support Files"` for a `-Core`-style twin, or archive.

**Invariant that keeps the memory story true: no bytes-heavy work in the
extension.** The extension handles URLs and KB-sized entity JSON only —
image/screenshot fetch, decrypt, and encrypt stay in the main app / extractor.
This is what keeps the DATA out of the footprint; it does not make the process
comfortable — the runtime alone leaves a dev build ~16MB short of the cap (_the
share extension has almost no memory to spare_, above). Don't move image work
across the process boundary to "save a round trip."

**Keep `index.share.js` lean.** Everything the share entry transitively imports
is init cost paid on every cold share (see the cold-start note in the file map
below). The extension bundle should pull in `ShareRoot`/`ShareScreen`, the
pickers and `share-store` — **not** the router tree, `_layout`'s providers, the
store/sync layer, or main-app-only modules. It is the one real lever on RN
cold-start latency, and it has to be policed with a tool, because a violation is
silent: nothing fails, Android can't reproduce it (its share activity rides the
main bundle, where every one of these modules is resident anyway), and the sheet
just boots slower on iOS.

**The rule is: name a FILE, never a barrel.** Metro does not tree-shake, and a
barrel module _executes_ everything it re-exports. Three of them are in reach of
this tree, and all three are now deep-imported through declared subpath exports
([architecture.md](./architecture.md), _the barrel is the API_):

- **Lucide** (`lucide-react-native/icons/x`) — the barrel is ~1700 icon modules,
  every one executed on import. The subpath is a declared package export with
  types (`./icons/*`), resolved under the `react-native` condition by Metro and
  jest alike, not a reach into `dist/`. `components/links/link-quota-banner.tsx`,
  which the sheet renders at the cap, follows the rule for the same reason.
- **`@stxapps/expo-react`** (`/data/share-store`, `/data/share-theme-store`) — its index is 60 `export *`s:
  every provider and hook, the sync engine, import/export. Through the barrel the
  extension was executing drizzle-orm, expo-sqlite, @tanstack/react-query,
  react-hook-form, fflate, expo-image-manipulator and expo-local-authentication,
  none of which it can call.
- **`@stxapps/expo-crypto`** (`/lib/ids`, `/lib/shared-keychain`) — its index
  pulls the AES + Argon2 stack, i.e. react-native-quick-crypto plus
  readable-stream, buffer and nitro-modules, for the sake of `newId` and three
  Keychain calls.

Type-only imports are exempt and stay exempt: babel erases them, and the bundle
confirms it. **The rest is enforced** by `@typescript-eslint/no-restricted-imports`
in `apps/bracemark-expo/eslint.config.mjs`, scoped to `features/share/**` plus
`link-quota-banner`, and it covers the ui components below as well. Prose in a
file header did not hold; the barrels sat in the bundle unnoticed until someone
measured.

**Lazy where the platform, not the module, decides.** Two modules the extension
DOES import have halves it never runs, and they defer them behind
`require()` at the call site rather than a top-level `import`:

- `share-store` keeps the write edge, the read queries, the item store, the
  cached plan and the sync engine lazy — that is the **Android + main-app** half
  (sqlite, drizzle), and it is most of the module's surface. `typeof import(...)`
  keeps the call sites typed; Metro still resolves the literal specifier, so the
  graph is identical and only the evaluation moves.
- `share-upload` and `newId` are lazy for a subtler reason: they belong to the
  iOS path, but only **after Save**. Deferring them keeps the whole quick-crypto
  stack off the cold path, where the user is waiting, and lands it on a tap that
  needs it anyway.

**No portals, no Reanimated.** The pickers are screens within the sheet rather
than overlays over it, and the specimen's corner cut is an overlay rather than a
stroked SVG path ([brand-assets.md](./brand-assets.md#the-mark), _at TILE scale_).
`react-native-svg` is in the bundle regardless — **every lucide icon renders
through it**, so this is not a cost the brand lockup adds and not one that
dropping the lockup would remove.

**The numbers, so a regression is legible.** Bundle
`index.share.js` for iOS (`npx expo export:embed --platform ios --entry-file
index.share.js --bundle-output /tmp/share.jsbundle --dev false`) and count the
modules Metro reports. As of the deep-import pass: **1452 modules, 2.96MB**
minified, of which roughly **640 execute at init** — down from 1661 / 3.65MB /
~1050 through the barrels. Modules in the bundle are cheap (Hermes bytecode,
paged in on use); modules EXECUTED at init are what the cold share pays for, and
the two move together only when an import is removed rather than deferred. What
remains eager is irreducible without a bigger change: zod and the `@stxapps/shared`
barrel (its endpoint contracts are what the upload speaks), react-native-svg (the
icons), and culori (uniwind's runtime).

### driving it from Safari — the one tap that lies

⚠ **`tapOn` the Bracemark entry in the iOS system share sheet reports COMPLETED
and does not launch this extension.** Measured twice on Maestro 2.8.0 / Xcode
26.6 / iOS 26.5 / iPhone 17 Pro, against a dev build, with the sheet open over
Safari:

```
Assert that "^Bracemark$" is visible... COMPLETED
Tap on "^Bracemark$"... COMPLETED
```

— while `xcrun simctl spawn booted log stream --predicate 'processImagePath
CONTAINS[c] "BracemarkShareExtension"'` stays empty. No `launched.` line, no
process; the sheet simply dismisses back to Safari. A **coordinate** tap on the
same element of the same sheet launches it every time:

```
BracemarkShareExtension[…] [com.apple.extensionkit:default] Extension
`…/Bracemark.app/PlugIns/BracemarkShareExtension.appex` … launched.
```

Nothing catches the difference. The assert before the tap is honest — the label
really is on screen. The tap's own exit status is COMPLETED. The next step runs,
against Safari, and a flow written to "verify the share path" stays green
forever without once entering this process.

**The workaround is a coordinate tap plus an assertion on the far side.** Read
the icon's centre off `xcrun simctl io booted screenshot` (it was `(245, 646)`
in 402×874 pt on the specimen above), tap that, then assert on something only
this extension draws — `Close`, or the current state's own line ("Sign in to
save links" for the no-session state). Never treat the tap's exit status as
evidence that the boundary was crossed.

Reading across the boundary was never the problem and still isn't: `maestro
hierarchy` sees the sheet's target (as `accessibilityText`, **not** `text` — a
selector written against `text:` finds nothing and reads like blindness), and
sees this extension's own tree once it is running, which is exactly how _text
renders at zero point_ above was diagnosed. Taps **inside** the sheet route
correctly too. It is the one gesture that crosses from Safari's process into
this one that fails silently.

`agent-device` is no help here. Bound to its session app, it reports Safari's
nodes as `[covered]` and nothing behind them — `snapshot --raw` included — so it
can neither see the share sheet nor anything in this process. →
[app-drivers.md](./app-drivers.md), _the agent-facing drivers_.
