## Why a second review

October’s review found that a cleanup in the web app could delete a link’s saved preview on every device because the link was missing from one of them. The link was missing because a file that failed its integrity check was being skipped. We fixed that route and said some older ones remained. This review follows that thread, and it follows the code we wrote since: the same cleanups for the mobile apps, and code that keeps the text of an article as a read-mode copy.

The limits from October still apply. It’s an AI-assisted review that we direct, not an external audit. Its decisions rest on reading source and on running our own code on a development machine: the unit tests, small probes, and mutation tests, never production or real users’ data. None of it has been retested on a running app or a device. The counts of saved decisions haven’t changed: 28 records, of which 4 are confirmed findings (all low), 19 need validation, and 5 were rejected.

Nothing below is a new record, and we should say why. A record is a claim that someone with less trust than you could cross a boundary. Every item below happens to your own library, after a file failed to open or changes arrived in an unlucky order. We report them as engineering problems with a stated consequence, and we don’t treat that as the same thing as safe.

## When a device deletes something because it is missing

Your library is a set of encrypted files, and each device keeps its own copy. Some tidying can only work by noticing what isn’t there: the web app deletes a link’s preview when the link isn’t on the device, and deletes image files that no link names. That is safe only if missing means gone.

Missing can mean other things. A file failed its integrity check and was skipped. A sync stopped halfway. The changes arrived in a different order than they were written. A clock was wrong. A cleanup that reads each of those as gone turns one device’s problem into a deletion on every device, because the deletion syncs.

October’s fix gave each device a record of the files it couldn’t open, and held the cleanups back unless that record is complete. Since then we extended the same cleanups to the mobile apps, which needed the app’s first local database migration, and added a recheck that opens a recorded file again after an hour, then a day, then weekly.

## What the second review found

A separate agent, starting from a fresh context, read the whole set. It found no ordinary path that deletes a file another device still names. The record, the gate on the cleanups, and the recheck did what they claim on the web and on mobile, in our test harness. Then it found what the record didn’t reach.

- **Writers ignored the record.** Only the cleanups read it. A link whose preview file couldn’t be opened looked like a link with no preview, so the app fetched a new one and uploaded it over the server’s copy. The recheck then saw a newer local file and dropped the path from the record. After the 30-day grace, the cleanup for unreferenced files could delete what the unreadable file had pointed to, on every device. The overwrite was in the web app until our release of 20 November. The deletion never reached a release.
- **A preview could reach the server before its link.** Changes go up in batches of up to 500, in path order, and a preview’s path sorts before its link’s. Between two batches, another device could see a preview with no link and delete it. This was in the web app until 20 November. In the cases we reproduced, the cost was a preview, which the app can fetch again.
- **The grace period used the device’s clock.** A clock set well ahead would shorten the 30 days.
- **Smaller ones:** the cleanup of device-local list locks deleted the lock of a list that was only unreadable; the grace counted from when a file was uploaded, not from the owner’s last change; and a replaced image was deleted before its replacement uploaded.

## What we changed, and how it was checked

We made the fixes and then had them checked the way we did in October: a separate agent, given the earlier review and the changed code, and not told what to expect.

- A link whose preview file is recorded as unreadable is no longer rewritten. A capture you start on one fails with a generic error until the recheck opens the file.
- Previews are queued after their links, so a batch boundary can’t separate them in the wrong order.
- The grace period can’t run ahead of the newest time the server has reported.
- The lock cleanup spares a list that’s recorded as unreadable.
- A cycle that fails partway no longer leaves the record marked complete.

The recheck found the routes closed, and no new deletion by absence. It also found small things, and two of them were ours: our new refusal could stop the iOS share-sheet drain from saving later drafts, and a refused write left files it had already uploaded with nothing pointing to them. We fixed both. That fix, and every change since the recheck, was read by us and by tests, not by a separate agent.

## What we decided to leave

- **A file that can never be opened is never deleted, and we don’t tell you.** There’s nothing you could do about a file you can’t open, and nothing about it that we could show. The cost is that on that device the cleanup of unreferenced files stays off, so those files stay until the file opens.
- **A restore on our side may look like a deletion.** If our server were restored to an earlier point after your devices had synced, a device can’t always tell a restore from something you deleted. Fixing that needs the server to number its log. It isn’t built, and the design record says so.
- **Some libraries share one custom image between links.** Earlier imports did that. Changing or deleting the image on one of those links removes it under the others. New imports give each link its own.
- **A replaced image is deleted before its replacement uploads.** If the upload then fails, the old one is already gone.
- **The 30 days count from upload.** A file’s grace starts when it was uploaded, not when its owner last changed the link, so a file can have less time left than you’d expect.
- **The mobile migration hasn’t run on a device.** We tested it against a file shaped like the first release’s, in the test harness only.

## Read-mode copies

The repository also holds code that keeps an article’s text, and optionally its images, as a read-mode copy, so you can read it after the page moves; the section on releases says which builds carry it. Its words come from a page someone else wrote, through the browser extension, the mobile capture screen, the iOS share sheet from Safari, or our link-extraction service, and a copy also arrives inside a backup or from another device. We asked what a stranger’s page could do with that.

**The format held.** A stranger’s page doesn’t become markup, script, an attribute, an unchecked address, or an image address through any of those routes. Text is drawn as text. A link is kept only if it’s an absolute http or https address, and it’s checked again when it’s drawn. Images come only from the pack stored beside the copy. We drew a hostile document and found no script in the result.

**The size didn’t.** The limits lived in the converter that builds a copy, and on two routes that converter runs inside the page. So a forged message from a page, a backup, or a compromised device could store a copy of any size: 200 KB of gzip that decompresses to 200 MB. On our server, a page of nested elements made the reader slow in proportion to roughly the cube of its depth, and an 11 KB page took three to six seconds. A hostile robots.txt cost 3.4 seconds for one answer.

We added limits where a copy is stored and where it’s opened, bounds on the image pack, a step budget for robots.txt, and depth and element limits in the link-extraction service. A second agent rechecked and found the work partly done. The service’s depth and element limits didn’t bound its cost: a 74 KB page passed both and took 23.5 seconds. The mobile app’s limit on how much a copy may decompress to didn’t bound memory, because the library decompresses a whole chunk before it can stop: 1 MiB of gzip took about 3 GB.

We fixed those and most of the smaller ones. The mobile app now feeds the decompressor in 4 KiB slices.

Our first fix for the link-extraction service didn’t hold, and a third agent, reviewing everything up to the code we planned to release, showed why. The fix estimated a page’s nesting from its text, and the parser nests some markup the estimate didn’t count, so pages of about 1 MB still took 7 to 11 seconds to parse. And the library that finds the article takes time that grows with the square of how many siblings it gathers: 59,000 short paragraphs side by side took 173 seconds. So the service now counts a page’s nesting with the same parser it reads the page with, before it builds anything, and stops at a limit. It counts how many children each element has, not only how deep it is. And our server now stops any request to the service that uses more than 5 seconds of processing, for a shape no check foresaw. The same agent found that the mobile app could stall on a malformed compressed copy, and that the iPhone share sheet read a copy’s file whole before checking its size. We fixed both.

A fourth agent rechecked those fixes. The new checks held, and the mobile and share-sheet fixes closed what they were for. But the service’s cost still had a gap: our checks didn’t count attributes, and the library also walks every attribute, comment, and run of text. A page with one paragraph carrying 155,000 attributes, 240 levels deep, passed both checks and took 207 seconds. Only the 5-second limit would have stopped it. We now weigh those too.

A fifth agent checked that change. The new weight held for the shapes it was built for, but some of the library’s slow work isn’t a walk at all: it copies an element’s attributes one at a time, compares a long title word by word with a long heading, and runs patterns that retry from every character of a long string. Pages built that way passed every check and took up to 135 seconds. We charged for the copies and for long text deep in a page, and made the rest take time in proportion to the page.

A sixth agent checked those fixes. The string work was right and now fast. But the library repeats some of its work: it rereads an embedded video’s attributes under every box around it, and it searches the whole page again, up to four times, when the article it finds is short. Our checks charged that work once, so a 19 KB page passed them and took 175 seconds. And charging long text by its depth turned away an ordinary long article. So we stopped predicting that work and now count it as it happens: the service counts the reads the library makes while it runs, and stops past a budget. Over 616 pages on our own disk, none is refused and a 1 MB article reads. Our checks still turn away some honest pages: a whole book on one page, or a very long article in which most paragraphs hold a link. They treat those as costlier than they are, and the browser extension can still keep a read-mode copy of them. Every page the reviews built to be slow took under 2.5 seconds in the service’s runtime. The 5-second limit stays, because the count only sees the reads we know to count. A seventh agent checked these last changes. It found that the count now stops every page the reviews built to be slow: the slowest one it lets through took 2.45 seconds, and the 175-second page now stops in under one. It found that one request’s count can’t mix with another’s. It also found that the count prices some pages too low, so one read can take about 3 seconds rather than under one. That’s a looser limit than we meant, not a missing one, and the 5-second limit still holds. We’ll correct the prices in a later release.

The same agent read two other changes. We found that the web app checked your opt-in to server extraction, waited for a local read, and then asked the service without checking again, so turning it off at that moment could let one more request go out. For site icons, this was in the web app until our release of 20 November. It now checks again after every wait, and the seventh agent found a test for each of those checks. And the mobile capture screen now keeps the page you’re looking at, not only the exact address you saved, so a shortened link that redirects can be kept. Its top bar shows which site you’re on.

Three things stay open. We chose the limits by running them over several hundred pages on our own disk, none of which they refused. Since then we have run them over 52 pages from the web, and they refused none of those either, but 52 pages are not the whole web. We haven’t seen the mobile capture screen’s new-window handling on a device. And a page in the Android capture screen can still start a download into your Downloads folder, as it could before. We also left three small ones that need a forged capture or a restored backup: the capture screen doesn’t cap how many images a capture names, the limits count characters rather than elements, and the browser extension refuses an honest copy with one very long block of text.

None of this was in a release before 20 November, apart from an early version of the browser extension’s capture in its 1.2.0 builds. The reader, capture in the mobile app, read mode in the link-extraction service, and every limit above arrive with the release of that day.

## What is in each release

On 20 November we deployed the web app, our API (the service behind sign-in, sync, and billing), and the link-extraction service with the fixes this post describes. The same day we sent an Android update to Google Play and a browser extension update to Chrome and Firefox. Each reaches you once its store approves it. Until then, the Android app on Google Play has the October fixes and none of this review’s. The iOS app is still waiting for its first App Store review, and that first version has none of this review’s changes either.

The release is built from a later revision than the one this post describes. It adds work on the screens around copies, the share sheet, and the list pickers. We read the changes that touch what this review covers, and so did the third agent: the iPhone share sheet now hands a copy to the app through a file, the capture screen and the reader were rearranged, and the web app syncs after you delete all data. Only the first needed a fix: the app read the copy’s file whole before checking its size, as described above.

## How we did it

The method is October’s: we adapted Cloudflare’s [security-audit skill](https://github.com/cloudflare/security-audit-skill), a separate agent from a fresh context reviews each claim and each fix of ours, and no third party has audited Bracemark. The session that ran the first of these reviews recorded that it ran on Claude Sonnet 5.5, and the reading of the release’s later changes ran on Claude Opus 5.5. The other sessions, and the separate reviewing agents, didn’t record which model they ran on, so we can’t name it.

## What this still doesn’t settle

Nothing here has been retested on a device or on a running deployment. Our one staging run held an older build of the web app, so it says nothing about these changes. Open facts that need a device or a deployment: the mobile migration on a real first-release database; Android’s handling of a page that opens a new window; whether the phone’s network stack reads a response in pieces; and how a deployed Worker’s CPU limit treats a page near the link-extraction service’s cap.
