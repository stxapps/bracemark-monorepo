## Why we started with the source

An encrypted sync path still has to handle an imported file, a cancelled operation, and a device that changes accounts while work is in flight. Encryption doesn’t make those transitions correct. We started reviewing the source to trace where outside input becomes stored data, where authority is checked, and what happens when work finishes later than expected.

The review is ongoing. Its decisions rest on reading source. Since 20 October a review may also run our own code where reading it can’t settle a question — the unit tests, small probes, and mutation tests, in a separate copy on a development machine — but never against production or real users’ data. No finding below has been retested on a running app, a device, or a deployment. That limit matters to every result below.

## How we used AI agents

We adapted [Cloudflare’s security-audit skill](https://github.com/cloudflare/security-audit-skill) into focused assignments. The skill gives an agent a way to map trust boundaries, examine a possible failure, and ask another agent to challenge the evidence. Cloudflare didn’t audit Bracemark.

Our recorded plan requested GPT-6.1 Sol with high reasoning for substantive review and verification. The history also includes Astra/high, Claude Opus 5.5, and sessions recorded only as the active Codex runtime. We can’t verify the exact model and reasoning setting for every session, so attributing the whole review to one model would be inaccurate. Our fixes, the rechecks of them, and every review since 12 October used Claude Opus 5.5.

For a surviving security claim, a separate agent worked from a fresh context. Its job was to test the claim against the source and the controls that might defeat it. We use the same arrangement on our own fixes: an agent that had not written them is given the original finding and the changed source, and isn’t told what answer to expect. That helps expose assumptions, but it remains an AI-assisted process we direct. We haven’t commissioned an external professional audit through this work.

We have recorded more than 300 completed bounded tasks. Some map a boundary, some verify a claim, and some reconcile changed source or prepare an engineering handoff. A task can finish with its decisive question still unresolved. The number records work done; it doesn’t tell you how much of the product is secure.

## What the review found

The saved decisions contain four historically confirmed findings, each with an overall severity of low. They concern backup file references, associated files left by refused import rows, imported dates, and deeply nested list structure. Their recorded consequences concern storage, sync, or access to the importing account’s links.

All four have source fixes, with tests that fail without them, and all four are in the build now in production.

- A file reference in a backup is checked against the format of a storage path before anything is written.
- A file attached to an imported row is chosen only after the row’s link is accepted, so a refused row no longer leaves a file behind.
- A date the calendar cannot represent is dropped from a row imported from another app, and refuses the line in a backup. The link list and the CSV export no longer fail on one that is already stored.
- An import from another app no longer creates lists nested past 100 levels, and the code that reads the list tree no longer needs a level of the call stack for each level of the tree.

Separate agents rechecked those fixes against the source and found our first attempts wrong in places: a timestamp checked on the wrong object, a sidebar that still nested once per level, a depth check that ran after a prompt it should have come before. We corrected each and had the corrections checked again.

Each fix covers what arrives from now on. None repairs a record that was stored earlier. Refusing a bad date in a backup also has a cost: a backup exported from an account that already holds one loses that link on restore. None of the four has a runtime retest.

No medium, high, or critical overall severity was assigned in the saved decisions. There are also 19 unresolved records without severity and five rejected claims, and six further hypotheses that our reviews raised and have not decided. Those could change the picture when the missing evidence is available. We therefore cannot describe the outcome as no vulnerabilities found. Low severity is still a finding. Missing evidence is still missing evidence.

## What we changed before launch

Three of the unresolved records gained a source fix before the first release. Each was rechecked by a separate agent, and each is in the production build.

- **Each synced file is bound to its storage path.** The account’s key proves a file is the account’s, but nothing tied it to the path it is stored under, so whoever answered a request could hand back one of your own files in place of another, and it would open. Every file is now sealed with its path, on web, on mobile, and in the native iOS and Android code. We made that change before the release because changing the file format afterwards needs a migration of every account. It doesn’t stop a server from serving an older version of a file or withholding one.
- **A link shared from the iOS share sheet is saved only under the account it was shared from.** Before, a draft could be saved under the next account if the account changed before the app took it in.
- **A backup cannot make one list appear many times.** A backup could give several lists the same identifier, and the tree built from it gave every copy its own copy of everything beneath it. A restore now refuses such a line, and the tree holds one entry per identifier.

## What we found after launch

The release also carried two changes we made in the week before it, and the reviews afterwards found that each had a cost we had not described. Both concern your own library, and both are low in severity.

**A file that fails to open is now skipped.** Before, a synced file that failed its integrity check stopped sync with an error. Now the app logs it and moves on. A review found that the binding to the storage path still holds, and that a server gains nothing it could not already do by withholding a file. But in the web app, a once-per-session cleanup deletes a link’s saved preview, everywhere, when the link is missing from the device. A link that was skipped was missing, so its preview could be deleted. We observed that by running the web sync code and the cleanup together in a test harness. Our fix records what was skipped and runs the cleanup only after a sync that succeeded. A separate agent reviewed it and found it closes those routes, and that a few older ways a link can be missing on one device remain, which the cleanup still cannot tell apart.

**Restoring a backup now places deep lists instead of refusing.** A line past 100 levels is placed at the 100th, so a restore keeps every list. The review found this holds the tree a restore stores to 100 levels, but that a loop of parents in the file hid long chains the restore didn’t measure, and one ordinary move afterwards could join them into a single chain as deep as the file. A probe of the restore’s shared code produced 19,802 levels from a file of that many lines. Our fix stores the loop as the screens already show it, cut, and has every move measure the tree after it, not before. A separate agent rechecked the fix on 21 October and found that it holds for that route: after a restore, none of the moves it tried — about 31,000 each for lists and for tags, and thousands more at random — took a tree past 100 levels. It also found that a loop can still be built across several restores, which the restore doesn’t see, and that the check on every move is what keeps it from being released.

Both fixes are committed and not yet deployed. When they are, they cover what happens from then on; a preview already deleted is not restored.

## What reading the source cannot settle

The work examined selected account and session paths, encrypted sync and storage, the preview service, import and restore, browser lifecycle work, native account transitions, and one payment event. It hasn’t established complete coverage of those areas or a comprehensive cryptographic assessment.

Source can show where a check runs and what data reaches the next operation. Running our own code on a development machine can show what a function does with a given input. Neither establishes whether native work survives a disappearing screen, how a provider enforces a limit, or which concurrent write wins on a running device. Those questions need evidence from the relevant runtime or deployment.

Some hypotheses remain unresolved for exactly that reason. We haven’t assigned them severity, called them fixed, or treated them as evidence that the surrounding code is safe. We also keep ordinary correctness and recovery observations separate from security findings: a suspicious schedule needs a concrete protected-resource consequence before it becomes one.

## What the next evidence has to be

Most of the open facts can be reached without touching production: our own code run against a local copy of our API — the service behind sign-in, sync, and billing — with test accounts, or a separate staging deployment with its own storage and its own test accounts. What neither reaches is production itself, a signed build on a physical device, and a provider’s own policy, and those stay named as gaps. More source tasks alone will not answer those questions.

As the evidence changes, the report needs to change with it: the source revision, the observed behavior, the fix status, and the checks still missing.
